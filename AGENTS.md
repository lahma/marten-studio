# AGENTS.md

Guidance for humans and AI agents working in this repository. `CLAUDE.md` imports this file, so keep it
the single source of truth.

This repository ships two MIT-licensed Razor Class Libraries, embeddable Blazor Server admin UIs that run inside
the host's own ASP.NET Core application (D30):

- **Marten Studio** (`MartenStudio`), for [MartenDB](https://martendb.io). A host adds `AddMartenStudio()` to its
  container and `MapMartenStudio()` to its endpoint pipeline, and the studio runs against *that application's own*
  configured `IDocumentStore` — browsing document collections and their JSON, inspecting and steering event
  streams, projections and the async daemon, running guarded queries and managing schema.
- **Postgres Studio** (`PostgresStudio`), for any application that registers an `NpgsqlDataSource`, Marten or not:
  `AddPostgresStudio()` and `MapPostgresStudio()`, against the application's own data sources. It is also the core
  Marten Studio is built on: the shell, the scope and authorization layers, the audit, the database browser,
  Sessions, the health advisor and its pages, the SQL console and Relationships are PostgresStudio's, and
  MartenStudio adds the Marten screens, the Marten checks and the Marten halves of every seam.

Neither is a standalone application, a fleet monitor or a connection-string tool. Everything Marten Studio
knows, it knows because the host configured Marten that way: aliases, duplicated fields, soft delete,
tenancy, projections and metadata columns all come from `StoreOptions`. That is the whole reason a Marten
UI is better than pgAdmin, and it is why the data layer is keyed on `IDocumentStore`, and Postgres Studio's on
the application's own `NpgsqlDataSource` registrations, and never on a connection string.

Two constraints govern every design choice here:

- **Registering either studio must never change host behaviour.** No global styles, no component-library
  version pinned onto the host, no middleware ordering requirement, no altered authentication, no second
  projection daemon. A host that adds a package and never maps it must be byte-for-byte the application it was.
- **PostgresStudio never references Marten, JasperFx or Weasel, and nothing it ships names them except as text**
  (hard rule 16). A host with no Marten must never get Marten through it.

The original product design — information architecture, every screen, the JSON viewer, the authorization
model, the phased delivery plan — is the approved plan at
`C:\Users\marko\.claude\plans\i-d-like-you-to-composed-galaxy.md`; 0.5's split and its public API are designed in

## Hard rules

1. **No new NuGet package without a decision recorded in this file.** The package budget below is
   complete. If a package looks necessary, add a dated entry to *Package budget changes*
   (`docs/maintainers/package-budget-changes.md`) saying what it is,
   what it replaces, and why nothing already present can do the job — before referencing it.
2. **Never hand-edit `.github/workflows/*.yml`.** All four — `build.yml`, `marten-latest.yml`,
   `publish.yml`, `release.yml` — are generated from the `[GitHubActions]` attributes in
   `build/Build.CI.GitHubActions.cs`, and any build
   run overwrites them. Change the attribute and re-run the build (`dotnet fallout
   --generate-configuration GitHubActions_publish --host GitHubActions` regenerates just one). A run whose
   generated output differs *aborts* with `Configuration files for GitHubActions (…) have changed` — run
   it again and commit the regenerated YAML. `WorkflowGenerationTests` fails if a file loses its
   `<auto-generated>` header or its load-bearing permission lines. The `marten-latest` attribute's `Env` is
   `MARTEN_VERSION: latest` and `NPGSQL_VERSION: latest`, so one workflow runs both latest legs (*Build*).
3. **No MudBlazor, and no third-party UI, CSS or icon library, ever.** Styling is hand-rolled, prefixed
   `ms-`, and driven by the design tokens in `src/PostgresStudio/wwwroot/css/studio.css`. There is still exactly
   one stylesheet, and it holds both studios' sections (D26). An
   embeddable component that injects global styles or pins a component-library version is a component that
   breaks the host's own UI on upgrade; that is the failure Quartz.Dashboard documented and this project
   inherits the rule from.
4. **No raw SQL outside the two builders' folders, `src/PostgresStudio/Internal/Sql/` and
   `src/MartenStudio/Internal/Sql/`.** Identifiers are quoted through the builder, values are always
   parameters. Marten only ever hands the studio a runtime `Type`, and the shared studio knows a relation only
   by its catalog name, so the reads *are* generated SQL — which means there is exactly one place per assembly
   where an interpolated identifier could become an injection, and each is small enough to review. The shared
   studio's builders, `SqlIdentifier` and `SqlLexer` among them, live in the first; the statements only a Marten
   store has (the document, event, daemon and projection reads) in the second, which calls the first's quoting.
   The compiled fence in `HealthQueryConventionTests` exempts each folder's namespace by name —
   `PostgresStudio.Internal.Sql` in `PostgresStudio.dll`, `MartenStudio.Internal.Sql` in `MartenStudio.dll` —
   and each **only in its own folder**, so the same test refuses a declaration of either namespace, or of one
   inside it, in any `.cs` or `.razor` file under `src/` outside that namespace's own folder, the other
   studio's folder included, comparing names as C# does (a leading `@` removed, Unicode escapes decoded,
   formatting characters removed).
5. **Every mutating operation, and every read authorized like a write, is capability-gated in the service layer,
   and audited.** (PostgresStudio has only the latter: `RunSql`, `BrowseDatabase` and `ViewDatabaseActivity`.)
   Hiding a button is
   a UI convenience; the refusal has to live where the operation does, because a Blazor circuit is a
   long-lived object a client can drive. `StudioCapabilityGuard.Require(…)` → scope resolution (with
   `WriteAuthorizationPolicy`) → the operation → `audit.Record`, written on failure as well as on success.
   A value a visitor could shape reaches the log only through `StudioLogValue`: escaped, a backslash doubled, a
   name bounded at 256 characters and other text at 4,000. That holds in these events: 9200–9205, 9235, 9236, 9245
   and 9452 (the per-product dispatchers); 9206, 9207 and 9209 (MartenLog's wrappers); 9260–9263 (LINQ mode's
   `Logged*` values); and every Warning that carries a typed route value. The one exception is 9204's executed
   statement, which is kept whole up to the circuit's 32 KB receive bound, and by its head and tail beyond it.
6. **No `async void`.** Component events are `Func<Task>`, handlers are `private async Task` with a
   `try`/`catch` that puts the failure on screen. An `async void` handler's exception escapes the
   synchronization context unobserved and kills the circuit: the page silently stops responding and the
   server log gets an unhandled exception with no component in the stack. `NoAsyncVoidTests` scans `src/`
   and fails on any occurrence. **The lambda form is equally forbidden and the scanner cannot see it:**
   `handler += async (s, e) => …` against an `EventHandler`, or any `async` lambda converted to an
   `Action`, is an `async void` with different spelling and fails in exactly the same way. That is why
   every event this codebase raises is declared `event Func<Task>?` rather than `EventHandler` — an
   `EventHandler` is what *forces* the mistake, so the type is the enforcement and the scanner is only
   the backstop.
7. **A public API change needs a reviewed Verify baseline and a CHANGELOG entry.** MartenStudio's surface is
   three static classes, two classes and one record, in
   `tests/MartenStudio.Tests/Verify/PublicApiTest_MartenStudio.verified.txt`, and it must not move because of
   PostgresStudio. PostgresStudio's is the same six (its own registration types), plus its six inbound types
   (`IPostgresDatabaseSource`, `IPostgresCapacitySource`, `PostgresComputeCapacity`, `PostgresDatabaseRef`,
   `PostgresServerInfo`, `PostgresPlatformKind`: two interfaces and their records) and the D31 read model's nineteen
   types, which `tests/PostgresStudio.Tests/Verify/PublicApiTest_PostgresStudio.verified.txt` lists type by type.
   Anything else that appears in either baseline is a mistake, not a feature.
   Never hand-edit a `.verified.txt`: run the test, read the diff deliberately, say in the pull request
   what moved and why, then accept the baseline. The read model is extend-only (D31), and `PublicApiShapeTests` holds
   it to that.
   **`docs/health/codes.md` is a contract too, and a row is never deleted.** Every registered check's code has its row,
   with its area, variants, subject kind, studios and the release that first shipped it. A retired check keeps its
   row, marked with the release that retired it, and its code is never reassigned. `HealthCodesTests` holds the table
   to both studios' registries, and its stable columns are a Verify baseline (`HealthCodesTests.verified.txt`), so
   editing or deleting a row is a reviewed baseline change under this rule's process. A new check adds its row in the
   same pull request as its `## <code> <title>` heading.
8. **`.gitignore` must never contain a bare `build` rule.** The Fallout orchestrator lives in `build/`,
   and a stock Visual Studio .gitignore silently untracks the whole thing.
9. **LF line endings everywhere** (`.gitattributes` enforces it), UTF-8 without BOM.
   `TreatWarningsAsErrors` is on and `CS1591` is an **error in `src/`**, both assemblies — the compiler is the lint step.
   `.editorconfig` turns CS1591 off again for `build/`, `tests/`, `samples/` and `*.razor`, where a missing
   doc comment is noise. `BL0005` (setting a `[Parameter]` from outside its component) is an error.
10. **In MartenStudio, Marten 9 is async-only, and its optional parts are genuinely optional.** There are no synchronous
    LINQ terminals — they throw. Serialize and deserialize through `store.Options.Serializer()`, never your own
    `JsonSerializer`, or a document round-trips through settings Marten did not write it with. Never touch
    `StoreOptions.Storage.AllDocumentMappings` (internal). Every metadata column is optional, and `Metadata.X.Enabled`
    alone does not say one exists: `tenant_id` exists iff the type is conjoined, `mt_doc_type` iff it is a hierarchy,
    `mt_deleted`/`mt_deleted_at` iff its `DeleteStyle` is soft (cast the `IDocumentType` to
    `Marten.Schema.DocumentMapping` to read it), only the rest honour `Enabled`, and `DisableInformationalFields()`
    removes `mt_last_modified`. Build the column set with
    `DocumentTableInfo.FromDocumentType(...).WithPhysicalColumns(...)`, which settles it against `information_schema`,
    and never `select *`.
    **And `IDocumentType.DuplicatedFields` is not a list of columns.** Each metadata column a Marten attribute names a
    member for (`[Version]`, `[CreatedAt]`, `[LastModified]`, `[TenantId]`, `[CorrelationId]`, `[CausationId]`,
    `[LastModifiedBy]`) also gets a *search-only* duplicated field, `OnlyForSearching`, named for the *metadata* column
    (`mt_version`) and creating no column. Whatever describes the table's columns enumerates
    `MartenDuplicatedFields.Physical`; only `MetadataAliases` (via `DocumentTableInfo.FindDuplicated`), the search path,
    may see the other half: a column named twice ends the circuit, not the render (issue #1). The fields appear *late*:
    none before a store builds its schema (every unit test here), all once it has served a query (every application).
    Test the shape with `SqlTestStore.WithLinqSearchAliasFor` and prove Marten's half live (history:
    `docs/maintainers/decision-notes.md`, hard rule 10).
11. **In MartenStudio, never call `store.BuildProjectionDaemonAsync()`.** It starts a *second* daemon alongside the host's
    own, and the two fight over the same advisory locks until one hangs. The only supported way to reach a
    running daemon is the DI-registered coordinator, and its absence is a value —
    `DaemonHosting.NotHostedInThisProcess` — not an error.
12. **The agent definitions in `.claude/agents/*.md` are the only way work is delegated.** A packet is
    routed to exactly one of them; ad-hoc prompting bypasses the rules those files carry (base-commit
    verification, the shared-files list, the reporting format) and produces work that cannot be validated.
13. **A packet routed to Sonnet (`studio-grunt`) must be fully specified** (D21). It may only be given work
    whose expected output the orchestrator can state outright — copy these files with these renames, emit
    this class from this table, run this command and paste the output. If a step needs a decision the
    packet does not make, the correct behaviour is to stop and report the question, never to guess.
14. **In MartenStudio, a read or navigation path never calls `AllSchemaNames()`, `AllObjects()`, `ToDatabaseScript()` or
    `CreateMigrationAsync()` — and nothing may describe `CreateOrUpdate` as additive.** (PostgresStudio's read paths
    write nothing, as `FirstNavigationLiveTests` in `PostgresStudio.Integration.Tests` proves for every core page.)
    Below Marten 9.50.3 the first two *apply migrations*, under the database's own `AutoCreate`, when a document type
    has a numeric or HiLo id: **a single `AllSchemaNames()` call on an empty schema creates `mt_hilo` and
    `mt_get_next_hi`**. From 9.50.3 (#5665) the enumeration is offline (`RuntimeFeature.OfflineSchemaEnumeration`); the
    rule stands at every version because the floor has the hazard, and `SchemaNoDdlLiveTests` pins both ends. The last
    two are slow, connection-hungry and still connect. **Nor does a read path run a Marten LINQ terminal**
    (`ToListAsync`, `CountAsync`, `FirstOrDefaultAsync` and the rest), `ToCommand`, `ExplainAsync`, `ToPreviewCommand`,
    `LoadAsync`, `LoadManyAsync` or a `session.Events` read such as `FetchStreamAsync` or `AggregateStreamAsync`: each
    calls `EnsureStorageExistsAsync`, which creates or migrates its type's storage (below 9.50.3, `mt_hilo` too) when
    the process first asks. Reads use the studio's own SQL; `StorageEnsuringCallTests` allows those calls only in the
    capability-gated writes and F7's LINQ composition, which `MartenLinqCommand` builds into SQL without it. From 9.52
    the projection-floor seam (`FetchProjectionFloorAsync` and its two setters) and the high-water advance ensure the
    event storage too: the rebuild dialog reads `mt_event_projection_floors` with the studio's own SQL, and the advance
    is a gated write. Schema names, declared indexes, managed tables, installed functions and what Marten owns (its kind
    map, D27) come from `SchemaDeclarationReader`, which reads `IReadOnlyStoreOptions`, `IDocumentType` and the event
    store's feature schema without a connection; `CheckAsync`, `PreviewAsync` and `DdlAsync` are behind buttons that say
    what they may create on the host's Marten. Everything schema-related is **per database, never per store**: the same
    four members on `IMartenDatabase` (via `Weasel.Core.Migrations.IDatabase`) answer for the resolved database only,
    while `store.Storage`'s apply reaches *every* database a `DynamicMultiple` store knows. Enumerating a dynamic
    tenancy's databases is not read-only either (D27's known limit; `TenancyEnumerationCallTests` fences its call
    sites).
    **`AutoCreate.CreateOrUpdate` is not additive**: its `Update` delta (Weasel's `TableDelta.WriteUpdate`) drops
    undeclared indexes and extra columns, retypes changed columns, drops a changed primary key `CASCADE` and rebuilds a
    re-partitioned table; only `Invalid` is refused. No screen, comment or doc may say an apply leaves a hand-made index
    alone. Apply and its preview run under `CreateOrUpdate`, never `AutoCreate.All`, so what is read is what is run.
    `MigrationRisk` lists the destructive statements before the typed confirmation, and notes two that remove nothing:
    an index built without `CONCURRENTLY` on an existing table, and Weasel 9.46's partition-index resume, whose
    `DROP INDEX CONCURRENTLY IF EXISTS` of an unattached child, rebuilt and attached at once, is not a drop. The typed
    string travels to the service, never re-supplied by the page. `Check`, `Preview` and `DDL` print the whole database
    (every tenant's partition, every document type's table), so they answer only a visitor the store policy allows for
    the database with `TenantId = null` and, while any document type is hidden, past the database browser's gate; an
    apply is authorized as `(db, null, ApplySchemaChanges)` whatever tenant is selected, as `CreateOrUpdate` reaches
    every tenant. History: decision-notes.md, hard rule 14.
    **The database browser reads the catalog, never Weasel.** Every list and description of a non-Marten object comes
    from `pg_catalog` (never `information_schema`, which hides what the role cannot touch), filtered by
    `nspname = any(@schemas)`, inside `ReadOnlySqlSession`, so `lock_timeout` keeps it off a migration's lock queue and
    `has_*_privilege` answers for `SqlConsoleRole`.
15. **In MartenStudio, open Marten sessions only with `SessionOptions.ForDatabase(resolved.TenantId, resolved.Database)`**
    (or `ForDatabase(resolved.Database)` where the scope has no tenant), never `Store.QuerySession(tenantId)` /
    `LightweightSession(tenantId)`: those ignore the selected database and throw `DefaultTenantUsageDisabledException`
    on a `MultiTenantedDatabases` store, and an unpinned session on a multi-database store reads the store's default,
    not the database the scope named and the audit recorded. **Never run a user-supplied clause through
    `Query<T>(string)` / `QueryAsync(Type, string)`**: Marten's `UserSuppliedQueryHandler` adds no tenant or
    soft-delete predicate, so a typed where clause reads every tenant's rows and every deleted one. A document type
    Marten registers `SingleTenanted()` whatever the store (`DeadLetterEvent` is one) has no `tenant_id` column and no
    Marten predicate: filter on its own `TenantId` property, and prove a sequence is in scope before handing it to an
    API with no tenant predicate. **In both studios, catch interop loss with
    `catch (Exception e) when (StudioLiveUpdates.IsInteropUnavailable(e))`** (a core helper), never a ladder of
    `catch` clauses: `JSDisconnectedException` derives from `Exception`, *not* `JSException`, so
    `catch (JSException) { } catch (InvalidOperationException) { }` misses what every closed tab raises, and an
    exception escaping a component's `DisposeAsync` abandons the rest of that disposal, leaving the
    `DotNetObjectReference` that pins the component undisposed and the page's `CancellationTokenSource` uncancelled. A
    filter still rethrows anything that is a real bug (history: decision-notes.md, hard rule 15).
16. **The core is Marten-free, and the fence is the assembly.** `src/PostgresStudio` references no Marten, JasperFx or
    Weasel assembly or package, directly, through a project or transitively: `PostgresStudioFenceTests` holds that line
    at the project files, the restore graphs (`obj/project.assets.json`), the built assembly's references and the
    test project's output folder, and MartenStudio.Tests' `CoreFenceTests` at the text the compiler does not bind
    (Razor markup, attribute values, crefs and a `MartenStudio` namespace named in a shared file). MartenStudio reaches
    PostgresStudio only through `InternalsVisibleTo`, and is packed with an **exact** dependency on its own
    PostgresStudio build (`[x.y.z]`, D30), which `Pack` asserts in the nuspec and `AddMartenStudio()` checks at
    startup. A page route belongs to one assembly of a studio, below that assembly's own compile-time root
    (`/postgres`, `/marten`), and the route table refuses a route two pages claim (`StudioRouteTableTests`).

## Design decisions (D1–D31)

Every one of these was taken deliberately. Reversing one is allowed; doing it without reading the
rationale is not.

**D1 — `net10.0` only.** Marten 9 targets net9.0 and net10.0, .NET 9 is out of support, and the build
template this repository came from is net10-only. A second target framework would double the test matrix
and the conditional-compilation surface to support a runtime nobody should be deploying.

**D2 — Interactive Server render mode only, and `IsTrimmable=false` said out loud.** Blazor Server is what
lets the studio run against the host's in-process `IDocumentStore`; WebAssembly would need an API surface
that is itself the security problem. `IsTrimmable=false` is stated in the csproj with a comment rather than
left to the default, because Blazor sets component `[Parameter]` properties by name and the document viewer
deserializes into types discovered from `IDocumentType.DocumentType` at run time — a trimmer told it may
cut has no way to see either.

**D3 — Two dependencies a package, and no upper bound on either: MartenStudio (`Marten`, floor `9.39.0`, and
PostgresStudio at exactly its own version), PostgresStudio (`Npgsql`, floor `8.0.3`, and
`Microsoft.AspNetCore.App.Internal.Assets`, floor `10.0.12`) - each plus `FrameworkReference
Microsoft.AspNetCore.App`.** Everything else either RCL needs (Blazor, SignalR, authorization, endpoint routing) is in
the shared framework, so neither pins an ASP.NET Core patch onto its host; nor does the assets pack, three `.js` files
and an MSBuild target with no `lib/`, no `ref/` and no runtime assembly (D22). No `Marten.AspNetCore`: its value is
ETag'd HTTP JSON writers generic over `T`, and the studio only ever has a runtime `Type`. MartenStudio has no direct
`Npgsql`, which arrives through `Weasel.Postgresql` and must not drift from it; PostgresStudio, with no Marten to bring
it, references `Npgsql` directly (*Build*). The Marten floor is a *security* floor (*Package budget changes*), tested
and packed as *Build* says. The studio compiles without the JasperFx source generator Marten bundles, so its public API
is the same whichever Marten built it.

**D4 — Capabilities are a class of booleans, all defaulting to `false`.** A freshly mapped studio is a
read-only browser; `o.Capabilities = MartenStudioCapabilities.All()` is the one-line, greppable opt-in, and
every disabled control names the exact property a host would have to set. This is Hangfire's
GHSA-7rq6-7gv8-c37h applied to the write axis: the dashboard that is dangerous by default is the one
someone maps without reading the docs. `PostgresStudioCapabilities` has three, all reads authorized like writes
(`BrowseDatabase`, `ViewDatabaseActivity`, `RunSql`), on the same terms.

**D5 — Three authorization layers, plus two process-wide switches.** `AuthorizationPolicy` decides who
gets in; `StoreAuthorizationPolicy` decides which store, database and tenant, resource-based and enforced
on **every** data call rather than only at the selector; `WriteAuthorizationPolicy` decides each mutating
call, against the same resource with the capability name attached. `ReadOnly` and `Capabilities` sit on top
of all three. A startup guard refuses a mapping that answered none of it, because "I forgot to add
`RequireAuthorization`" must not be a silent state. Postgres Studio has the same three layers and the same guard, with
`SourceAuthorizationPolicy` asked about a `PostgresStudioResource` in place of the store policy (D30).

**D6 — Reads are raw parameterised SQL, writes go through a Marten session.** The studio only knows
document types as runtime `Type`s, so a generic `session.Query<T>()` is not available to it; reads are
built from `IDocumentType` metadata against `IMartenDatabase.CreateConnection(ConnectionUsage.Read)`.
Writes are the opposite: `StoreObjects(IEnumerable<object>)` / `DeleteObjects(IEnumerable<object>)` (both
verified non-generic) keep metadata columns, soft-delete semantics and tenancy exactly as Marten defines
them. The studio never hand-writes document DML; writes go through the session — re-implementing Marten's
write path is how a UI corrupts a store. (There is no `mt_upsert_*` function to call anyway: Marten 9.35
installs none, and the upsert is inline SQL in the generated write path — verified against a live schema
by P7, 2026-09-14.)

**D7 — Document edit shows a round-trip diff before saving.** Marten has no untyped store API, so saving
an edited document means deserializing into the CLR type and serializing it back: any property the type
does not have is *gone*. The dialog lists dropped, changed and added properties before the save happens.
Making the loss visible is the honest answer; silently dropping data is not, and refusing to edit at all
would make the feature useless for the schemas that need it most.

**D8 — Counts are `pg_class.reltuples` estimates by default, prefixed `~`.** An exact `count(*)` on a
10-million-row collection is a sequential scan, and a dashboard that does one per collection per refresh is
a denial of service against the database it is supposed to help you understand. Exact counts are available
on demand, under `statement_timeout`.

**D9 — Document and stream ids travel in the query string.** The hand-rolled router has no catch-all
segment, and Marten ids are frequently strings that contain `/`. Scope (`?store=&db=&tenant=`) lives in the
URL for the same reason a document id does: a link someone pastes into a chat has to reopen the same thing.

**D10 — No SignalR hub in v1.** Pages poll with a `PeriodicTimer` at `RefreshInterval`, paused on hidden
tabs, through a single-flight snapshot cache so that N circuits cost one query per interval rather than N.
Where the daemon is hosted in this process, a lazy observer on `ShardStateTracker` gives sub-second
projection state without any of that. The convention builder already carries an optional hub slot for v2;
adding a hub now would add a host-visible endpoint for a feature that polling covers.

**D11 — Sub-path mounting is ported from Quartz.Dashboard.** Compile-time routes are re-rooted at map time, from
each assembly's own root (`/postgres` for PostgresStudio's pages, `/marten` for MartenStudio's), and `/_blazor`,
`blazor.web.js`, `opaque-redirect` and `_content/PostgresStudio` - the shared assembly's assets, whichever studio
is mounted - are mirrored under the mount path (`StudioEndpointMapper`). Endpoint display names keep the
compile-time template, so no log or diagnostic text is ever built from one. This is ~250 lines of genuinely fiddly engineering that already works in production
somewhere; rewriting it would be the single most likely way to ship something that renders locally and
404s behind a path base. There is no "integrate into the host's own Blazor app" mode in v1.

**D12 — The data seam is internal, across both assemblies.** Per-area service interfaces (`IDocumentDataService`,
`IEventDataService`, …) with `InternalsVisibleTo` for the test projects - and, from PostgresStudio, for MartenStudio
(D30). Each package's *registration* surface is three static classes, two classes and one record, snapshot-tested;
PostgresStudio's also carries its inbound types and the D31 read model, which are results and hooks, never seams
(hard rule 7). Everything a consumer can bind to is everything we have to keep working.

**D13 — The SQL console is off by default, and its real guard is the transaction.** `RunSql` is a
capability like any other. What makes it safe is `SET TRANSACTION READ ONLY` plus `statement_timeout` and
an optional `SET LOCAL ROLE`, not the statement parser — the parser exists to produce a nicer error
message, and treating it as the security boundary is how these features get CVEs. `README.md` says it
plainly: grant it to people you would give `psql` to.

**D14 — No live SQL tail in v1.** It would require replacing the host's `StoreOptions.Logger`, which is
exactly the "registration changes host behaviour" failure this project refuses, and Marten 9 defaults
`DisableNpgsqlLogging=true` anyway. Every studio-generated grid carries a "Show SQL" disclosure instead,
which answers the question people actually have.

**D15 — Fallout 10.4.0 stable, CHANGELOG.md as the version authority, all four workflows generated,
trusted publishing for nuget.org.** See *Build* and *Release engineering* below. The important half is that
the version lives in one file that a human edits and no tool rewrites, and that the only credential
anywhere in the release path lives for minutes.

**D16 — xunit.v3 3.2.2 and Verify.XunitV3 32.0.0, four test projects all matching `*.Tests`.**
`tests/MartenStudio.Tests` and `tests/PostgresStudio.Tests` are fast and need no Docker;
`tests/MartenStudio.Integration.Tests` and `tests/PostgresStudio.Integration.Tests` need Testcontainers and
Playwright. PostgresStudio's two have no Marten anywhere in their graph. All four match the glob in
`ITest.TestProjects`, so one `dotnet fallout Test` runs everything. The pins are load-bearing — see *Package budget
changes*.

**D17 — The demo domain lives in `samples/MartenStudio.SampleDomain` and does not reference
`MartenStudio`.** It is shared by the sample host and by the integration tests, which is the reason it is a
project rather than a folder. The missing reference is deliberate and structural: the studio must work
against a store that knows nothing about it, and a reference here would let that invariant rot without
anyone noticing. Since 0.5 the demo data with no Marten in it - the relational demo schemas and the tenant
databases - is `samples/PostgresStudio.SampleData` (Npgsql only), which `MartenStudio.SampleDomain` and the Postgres
Studio sample both reference; it references no studio either.

**D18 — The sample host starts a throwaway Postgres when no connection string is configured.** Zero-config
`dotnet run` is what makes the sample a demo rather than a setup exercise. It prints a loud banner saying

**D27 — The database browser: one capability, one schema filter, and Marten's tables are never read raw.**
It lists the database's other objects by kind, gated like `RunSql`, whose power it is: `Capabilities.BrowseDatabase`
(off by default and under `ReadOnly`) and `BrowsableSchemas` (exact names, or `"*"` for every schema the role has
`USAGE` on but Postgres' own and extensions'). The store's *own* schemas' structure (names, columns, keys, indexes,
trigger names, estimates) needs neither, as the Schema screen shows it; everything else, every non-Marten definition and
every row needs both, plus the write policy asked **with `TenantId = null`**, as nothing filters a non-Marten table by
tenant. Marten's document and event tables and `mt_` objects are never read raw (the browser links to Documents and
Events, where tenancy, soft delete and the serializer apply), but the rows of flat-table projections and
`ExtendedSchemaObjects`, Marten-managed *relational* data, are browsable. A hidden document type
(`IsDocumentTypeVisible`) is absent from every list with its indexes, keys, triggers and partitions, and a view over its
table is refused; per-tenant partitions and sequences roll up, their names being the tenant list. Classification fails
closed: if a registered store's declarations cannot be read, nothing is "Other"; a `Storage.Add(IFeatureSchema)`
feature, which only Marten's internal `AllActiveFeatures` reaches, is classified by its `mt_` prefix. `BrowsableSchemas`
limits the screens, not `RunSql`: `SqlConsoleRole` is the real boundary, and `"*"` without it is event 9230 at startup.
Free text is masked and structure blanked: every catalog read pins `search_path` to `pg_catalog`, so deparsed names
carry their schema, and `WithheldNames` masks a withheld schema's qualifier as `‹withheld›` in types, defaults, CHECK,
index, view, routine and trigger definitions, `SET search_path` and comments. A view reading from or referring to a
withheld schema is refused its rows and query, as is a trigger with a withheld function and, while any document type may
be hidden, a view calling user code or reading a document table no store declares.
**A list locks nothing it lists** (no `pg_partition_*`, `pg_sequence_last_value` or size function): a tenant-partitioned
store has thousands of partitions, and the lock table is shared. Lists read `pg_catalog.pg_sequence`, never the
`pg_sequences` view, which on PostgreSQL 18 locks every sequence for every reader; a sequence's value is read on demand,
one at a time, behind `has_sequence_privilege`, which on 18 keeps the `RowExclusiveLock` away. Nor does a list call a
deparse function that opens what it describes, as its `AccessShareLock` queues behind a migration's `ACCESS EXCLUSIVE`
on 14 to 18: `pg_get_indexdef` in any form, `pg_get_expr` with a relation (a default's `adbin`, a partition's
`relpartbound`: `pg_get_expr(relpartbound, <relid>)`), `pg_get_viewdef`, a table CHECK's `pg_get_constraintdef`,
`pg_get_partkeydef`. Lists read partition bounds with `pg_get_expr(relpartbound, 0)`, which opens nothing
(`LintMatrixLiveTests`). A list that must deparse reads `pg_locks` once and leaves a locked table's text out
(`HealthTableQueries.IndexesSql`); a by-oid detail read may wait for its one relation, under `lock_timeout`.
Another store's key, alias and name in the "could not be built" notice show only to a visitor its store policy passes,
its Marten-managed rows need its store and write policies, and other stores' databases are enumerated only when a store
policy (or, while `BrowseDatabase` is on, a write policy) will be asked, never for a `DynamicMultiple` store. No rows
are read from a foreign table, a partitioned table with a foreign partition, a table with a foreign inheritance child or
a view reading one (a materialized view's rows are local, and read); from a view over Marten's tables or another store's
whose policies refuse the visitor; or from a table or view with partitions or children in a withheld schema. A view is
judged on what it reaches through views and SQL-standard-bodied functions (Postgres records their dependencies), the
schemas it names as values, its collations and its text search objects. A source-text function cannot be followed, so a
view calling one is refused its rows while any schema the reading role may read is withheld (for `SECURITY DEFINER`, any
schema): hence the sample's `legacy.format_employee_name` has a `RETURN` body. A schema an extension owns needs an exact
`BrowsableSchemas` entry, and one not admitted is masked like a withheld schema without counting as withheld for
dependencies. Known limits (in the notes): routine bodies' own name resolution, hidden types Marten has not learned
(`Schema.For`, `AllKnownDocumentTypes()`), domain CHECK functions, schemas newer than the 60-second cache, source-text
functions under `"*"` with a narrowed `SqlConsoleRole`, dynamic-SQL table names, foreign partitions under a minute old.
The first read of a relation's rows per signature (filter, sort, paging mode, never the cursor) is audited per store,
database and relation, never from a static render: browser pages read only once interactive and once their address's
scope applies, so a refused explicit request is one 9202/9203 per page view and a page whose gate is closed refuses
nothing. Activity and the Overview show an entry under `BrowseDatabase` or `RunSql` only while the capability is on and
the write policy passes the reader for its scope; a browser read the store policy refused is recorded under
`BrowseDatabase` too, each policy asked once per scope per sweep. Postgres' error text about a browser read is masked
like everything else except a value the read bound, echoed as typed; the Schema screen withholds a failure's text
outright when it cannot read the schema list to check it, and a failed apply's Activity entry carries its SQLSTATE, the
words staying in event 9206. Row reads do not pin `search_path`: a bare `=` must find `citext`'s own operator, and an
unqualified name names no schema.
**Reach, not scope.** An operation Marten runs over a whole database (a progression correction, a rebuild, a high-water
restart, a store-global agent, cancelling a rebuild, the dead-letter "Rewind subscription", a schema apply) is
authorized as `(store, database, null)` unless the database is exclusively the selected tenant's, never on a sharded
tenancy, which pools tenants; the SQL console, the Mode A subquery lift and `EXPLAIN` are always asked with
`TenantId = null`, as nothing narrows a typed statement to a tenant. The one exception is the dead-letter rewind under
`UseTenantPartitionedEvents` from Marten 9.51 with JasperFx 2.91 (`RuntimeFeature.TenantSubscriptionRewind`), whose
per-tenant overload touches only that tenant's agents and dead letters (#5700, jasperfx#1025): it is authorized as
`(store, database, tenant)` and made only for an agent this process's daemon runs, with that agent's own names, as the
overload starts the tenant's agents wherever it is asked. There the store-global rewind is never made, and Skip event is
`MarkEventsAsSkipped`'s tenant overload (#5698), asked about the tenant; below either version both stay refused
(SEC1-fix4). A tenant's database is found without asking a dynamic tenancy for a tenant it lacks
(`DatabaseReach.FindTenantDatabaseAsync`). Enumerating a dynamic tenancy's databases (`AllDatabases()`,
`Tenancy.DescribeDatabasesAsync()`, 9.50.1's `IEventStore.TryDescribeDatabasesAsync()`) is not read-only at any Marten
through 9.54.1, and the studio, enumerating on the first navigation, can be the first caller: a known limit, not a
per-poll cost. Measurements, history and details: decision-notes.md, D27.
**D27 in PostgresStudio.** The gate is reused with the source policy and `PostgresStudioResource` (D5),
`BrowsableSchemas` playing "the store's own schemas": the schemas it names exactly are the source's own, their structure
shown to anyone the source policy admits, their rows and definitions needing `BrowseDatabase` and the write policy

**D30 — PostgresStudio: the core is a package of its own, and Marten Studio is built on it.** 0.5 splits the studio into
two Razor Class Libraries, so a host with Marten gets one copy of the core and a host with only Npgsql takes the core
alone, as the user asked. **PostgresStudio** is everything about a PostgreSQL database rather than a Marten store: the
introduction's list, plus the router and re-rooting (D11), the capability guard, the Statements, Maintenance, Storage,
Replication and Server pages, the diagnostics API (D31), the JSON toolkit, the stylesheet, the script and the shared
checks (D29). Its references are D3's, and hard rule 16 fences them.

*Why `InternalsVisibleTo` and an exact pin, not a public extension API.* Marten Studio extends nearly every core
service, and publishing those seams would multiply the public surface (hard rule 7) for a plug-in model nobody asked
for; with IVT the two packages are one program in two files, as the nuspec's `[x.y.z]` says (*Build*).
`AddMartenStudio()` first runs `PostgresStudioVersionGuard` (*Build*; evidence: decision-notes.md, D30), which names no
PostgresStudio type and loads the assembly by name; the public `AddMartenStudio`'s own body stays free of PostgresStudio
types (the rest is in a `NoInlining` method), and `PostgresStudioVersionGuardTests` scans its IL to keep it so.

*What PostgresStudio browses.* The application's own singleton `NpgsqlDataSource` registrations, never a connection
string (see the introduction): the unkeyed one by default (`IncludeDefaultDataSource`, the source `default`), a keyed or
otherwise-held one named with `AddDataSource`, and a host's own databases named with `AddDatabaseSource` and an
`IPostgresDatabaseSource` that lists names and hands back each one's data source on demand. A factory is called once,
with the root provider, and its result kept for the process and never disposed; a scoped or transient registration is
refused, as it would build a pool per visitor. A database's identity is its source's own (a Marten store database's
`Id.Identity`, unchanged; a DI-registered data source's registration name; the name a host lists); `?db=`, policies,
caches, history, mutes and the audit key on it, so it must be stable across processes and restarts.

*Authorization.* Postgres Studio is asked against its own `PostgresStudioResource(SourceName, DatabaseIdentifier,
Capability)`, which has no tenant and is deliberately unrelated to `MartenStoreResource`: a handler written for one must
never be handed the other. `SourceAuthorizationPolicy` is its store policy; D27 applies as *D27 in PostgresStudio* says.

*Routes and assets* follow hard rule 16 and D11 (the shared pages sit at `/marten/…` in Marten Studio); static assets
live only in `_content/PostgresStudio/`.

*Words.* Shared sentences come from `IStudioSettings.Text` (`StudioText`): MartenStudio's instance is 0.4's literals,
pinned by `StudioTextPinTests`, so no Marten Studio host sees a word change. Shared log events keep MartenStudio's
templates in `StudioLog`; `PostgresStudioLog` declares the same ids, levels and properties in Postgres Studio's words.

*One studio per process in 0.5.* `AddPostgresStudio` and `AddMartenStudio` refuse each other, and each `Map*Studio`
refuses the other's registration (what the seams leave room for: decision-notes.md, D30).

**D31 — The diagnostics API: what the studio found, for the host's own code, by stable code, and never served by the
studio.** History: decision-notes.md, D31. `IPostgresDiagnostics`, registered by `AddPostgresStudio()` and by
`AddMartenStudio()` (one per process, like the studio), lists the databases the studio would list (`ListDatabasesAsync`)
and returns each one's `PostgresDiagnosticsSnapshot` (`GetSnapshotAsync`): findings by stable code and variant, and
typed sections for storage, statements, settings and extensions, and connections. `IPostgresDatabaseSource` (D30) and
`IPostgresCapacitySource`, found in DI to report compute capacity SQL cannot see (Aurora Serverless v2's ACU), point the
other way. MartenStudio's hosts reach it through the PostgresStudio assembly their exact pin names (hard rule 7).

*Why public, when D12 keeps the data seam internal.* It is results, not seams: with no `IStudioDatabase`, sweep or check
base class, a host cannot add a check or change a threshold (a non-goal of #8). The studio stays English; a host words
findings in its own language, keyed on codes.

*No visitor, so no visitor's gates, and no new reach.* The API answers host code, which already holds the data source or
the store, so it reads nothing that code could not: the pages' statements, as the same roles (`SqlConsoleRole` for all
but D29's first exception, whose `userid = current_user` fence holds), through the same single-flight caches. It skips
the per-visitor decisions (the store, source, write and authorization policies, the capabilities, `ReadOnly`, which is
about the people who open the studio, and D27's masking of withheld schemas) and keeps the content rules: no hidden
document type is named; a statement text still carrying a literal, or not a plain query or write, is withheld; comments
are masked; texts are capped; Postgres' error words are not carried, only the studio's sentence and the SQLSTATE.

*Activity-grade data is opt-in per call.* What D29 puts behind `Activity` (the statements section, application names,
other sessions' evidence, Activity checks' findings, findings about one tenant) is returned only when the call sets
`IncludeActivity = true`, else counted as withheld, as a visitor short of that gate is told: a section by name in
`Withheld`, a finding in `FindingsWithheld`, evidence by its label. The default is the safe one, for D4's reason: a call
written without reading the docs must not put statements in an e-mail.

*The studio never serves it.* Nothing in either package puts an API result into an HTTP response, a log line above
Debug, a metric, the Activity ring or the health check's data, and no endpoint maps one: where a result goes is the
host's decision. So the opt-in health check stays codes and counts (D29's second exception); the Health page's Snapshot
download is built from the visitor's own gated view, section by section, never from this API (`VisitorSnapshotBuilder`,
fenced by `DiagnosticsApiIsNotServedTests`); and an API call is not audited, as host code is not a visitor: a call is
event 9250, at Debug, codes and counts only.

*Stable codes.* A code is a letter and two digits, a string, never an enum, never reused, renamed or moved to another
area (hard rule 7). A finding's variant (`deadlocks`, `temp-files`) is frozen the same way within its code, and a check
with variants names one on every finding. Severity, category, outcome, action kind, platform and table ownership are
enums with explicit values, and may gain members.

*Extend-only* (hard rule 7). Result types are sealed, non-positional records with `init` properties and no `required`
member, so a host can build one in its tests and a new property breaks nothing. A new section is a new nullable property
and request flag; the three interfaces gain members only as default interface members. The JSON snapshot's
`schemaVersion` changes only for a removal, a rename or a change of meaning.

*Cost and DDL.* An API nobody calls reads nothing. Calls share the pages' sweep and section caches, so polling every few
seconds costs one sweep per interval per database; fresh reads that calls start run at most two at a time per process,
and a cache hit waits behind nothing. Listing never enumerates a tenancy that builds: Marten's databases are the held
ones (D27, hard rule 14). A host's database source must list without creating anything, and its names (D30's identities)
survive a database moving server. Per-database state is kept for at most 64 databases, least recently used forgotten
first (`HealthDatabaseBound`).

## Build

The orchestrator is [Fallout](https://fallout.build) 10.4.0 (stable channel), the maintained hard fork of
NUKE. The CLI is pinned in `.config/dotnet-tools.json` as `fallout.globaltool` (command `fallout`) and
resolves `build/_build.csproj` by folder-name convention.

**10.4.0 is not stale, and 11.0.x is not an upgrade.** Fallout runs two channels: `11.0.x` is *edge* and
`10.4.0` is *stable*, which is newer and a feature superset despite sorting lower. The edge CLI ships under
a different package id (`Fallout.Cli`), which is why `fallout.globaltool` has no 11.x and nothing is
behind. Moving `build/` to 11.0.x would fail to compile — `GitHubActionsAttribute.Env`, which `NUGET_USER`
depends on, does not exist there — and would regenerate the workflows backwards to older action versions.
Do not "update" it.

```powershell
.\build.ps1 Test                           # restore, compile, install browsers if asked, run all four test projects
.\build.ps1 Test --playwright              # ... and install Chromium first (D19)
.\build.ps1 Test --marten-version latest   # ... at the latest-tested Marten instead of the floor
.\build.ps1 Test --npgsql-version latest   # ... and then PostgresStudio's projects at the latest-tested Npgsql
.\build.ps1 Pack                           # both NuGet packages into artifacts/packages (always at the floors)
.\build.ps1 Browsers                       # just the Chromium install
```

`CHANGELOG.md` is the **version authority**: its top section is parsed in `OnBuildInitialized` and passed
to every compile, test and pack as `-p:Version=`. The file is never mutated by the build, and its first
line must parse as a version header (`# 0.1.0`) — **do not add a `# Changelog` title**, it would abort the
build. `Directory.Build.props`'s `VersionPrefix` is only the fallback for a plain `dotnet build`.

**The Marten version is `Directory.Packages.props`'s, and the build only chooses between two.**
`MartenStudioMartenFloor` (what the package depends on) and `MartenStudioMartenLatest` (the newest 9.x CI
tests, an exact version) are defined there once; `Marten`'s `PackageVersion` reads
`$(MartenStudioMartenVersion)`, which defaults to the floor. `build/Build.Marten.cs` resolves
`--marten-version` (env `MARTEN_VERSION`) — `floor`, the default; `latest`; or an exact version such as
`9.54.1`, never a range — in `OnBuildInitialized`, and passes the result as
`-p:MartenStudioMartenVersion=` to Restore, Compile and Test, the floor included, so an environment
variable of that name cannot change what a run tests. Without Fallout, `dotnet test …
-p:MartenStudioMartenVersion=9.54.1` does the same. **`Pack` packs at the floor and refuses anything
else**, twice: the Fallout target asserts it, and `MartenStudio.csproj` fails a bare `dotnet pack` before
the nuspec is written unless both `MartenStudioMartenVersion` is the floor *and* `project.assets.json`
holds the `"Marten/<floor>"` library — because NuGet writes the dependency range from the assets file,
so `dotnet test … -p:MartenStudioMartenVersion=9.54.1` followed by `dotnet pack --no-restore` would
otherwise pass a property check and still ship `Marten >= 9.54.1`. A missing assets file is a refusal,
not a pass (a package packed at a newer Marten would raise every host's floor). To bump the
latest-tested version: change `MartenStudioMartenLatest`, run both suites with `--marten-version latest`,
and fix or record every difference in the same pull request. Raising the floor is a *Package budget
changes* entry, never a side effect.

**PostgresStudio's Npgsql is `Directory.Packages.props`'s too, and anything but its floor gets a pass of its own.**
`PostgresStudioNpgsqlFloor` (8.0.3, what the PostgresStudio package depends on; never above the Npgsql that Marten's
own packages already require at the Marten floor, which `NpgsqlVersionTests` reads from MartenStudio's restore) and
`PostgresStudioNpgsqlLatest` (10.0.3) are defined there once, and the `Npgsql` row reads `$(PostgresStudioNpgsqlVersion)`
only for a project that sets `PostgresStudioPinsNpgsql`. `build/Build.Npgsql.cs` resolves `--npgsql-version` (env
`NPGSQL_VERSION`) - `floor`, the default; `latest`; or an exact version - but the whole-solution Restore, Compile and
Test always get `-p:PostgresStudioNpgsqlVersion=<floor>`: handed to the solution, a higher Npgsql reaches MartenStudio
and its tests through the `ProjectReference` with no diagnostic (PS-0), and MartenStudio on Npgsql 10 is not a tested
combination. Anything but the floor adds `NpgsqlPass`, which `Test` triggers: a separate restore, build and test over
`postgres-studio.slnf`, which holds exactly the projects that set the property and reaches nothing outside itself
(`PostgresStudioSolutionFilterTests`); each test project's TRX is `<project>.npgsql-<version>.trx`, beside the floor
pass's. `marten-latest.yml` sets `MARTEN_VERSION: latest` and `NPGSQL_VERSION: latest`, so one workflow runs both
latest legs. Without Fallout: `dotnet test postgres-studio.slnf -p:PostgresStudioNpgsqlVersion=10.0.3` - never the
`.slnx`. A project that sets `PostgresStudioPinsNpgsql` goes into `postgres-studio.slnf` in the same pull request.

**Two packages, one version.** `Pack` packs `src/PostgresStudio` and then `src/MartenStudio`, one after the other,
both at the CHANGELOG version and both at the floors - it refuses a `--marten-version` or `--npgsql-version` that is
not the floor, and each csproj refuses a bare `dotnet pack` off its floor, by property and by `project.assets.json` -
and then asserts both nuspecs. MartenStudio depends on exactly `PostgresStudio [<version>]`, on `Marten <floor>` and
on `Microsoft.AspNetCore.App.Internal.Assets` (written there by transitive pinning); PostgresStudio on
`Npgsql <floor>` and `Microsoft.AspNetCore.App.Internal.Assets` and nothing else. The exact range is
`MartenStudioPinsPostgresStudioExactly` in `MartenStudio.csproj`, which brackets NuGet-private item metadata; the
nuspec assertion is what turns a NuGet that renamed it into a red build rather than a shipped `>=`. NuGet enforces the
pin everywhere but one place: with `CentralPackageTransitivePinningEnabled` and a central `PackageVersion` for
PostgresStudio at another version, the SDK drops PostgresStudio from the graph without a warning (PS-0;
NuGet/Home#14698). So `AddMartenStudio` first runs `PostgresStudioVersionGuard` (D30), which throws an
`InvalidOperationException` naming the central pin when PostgresStudio is missing or its informational version
(before the `+`) differs.

`build/_build.csproj` restores with `NU1902`/`NU1903` warnings for `System.Security.Cryptography.Xml` and
`System.Security.Cryptography.Pkcs` 10.0.10, which `Fallout.Components` 10.4.0 brings transitively (seen
2026-10-15). They are warnings in the orchestrator only — it does not inherit `TreatWarningsAsErrors`, and
none of it ships — and pinning either package forward would be a budget decision this file has not taken.

The build needs at least one commit: `IHasGitRepository` injects `GitRepository` from the working tree and
fails with `Could not find commit information` on an empty repository.

## Release engineering

A release is cut by pushing a `v*.*.*` tag, which starts **two independent workflows**: `publish.yml`
(nuget.org) and `release.yml` (the GitHub Release). Neither depends on the other, deliberately — a
nuget.org outage must not hold up the release notes, and a release-API hiccup must not hold up the package.

They are separate files because of what each is allowed to hold. A nuget.org trusted publishing policy is
scoped by repository plus workflow **file name** (plus environment), and the nuget.org UI offers no branch
or tag filter — so whichever file the policy names can mint a publishing key on *every* run of that file.
`publish.yml` therefore runs only on a `v*.*.*` tag and holds `id-token: write` with `contents: read`;
`release.yml` holds `contents: write` and `GITHUB_TOKEN` and is not the file the policy names. **The one
workflow that can mint a key must not also hold repository write.** `WorkflowGenerationTests` asserts both
halves, in both directions.

`build.yml` and `marten-latest.yml` — every push and pull request to `main`, at the Marten floor and at
the latest-tested Marten — cannot mint anything, because neither is the file in the policy; both hold
`contents: read` and nothing else, and `WorkflowGenerationTests` asserts that no workflow but `publish.yml`
so much as mentions `id-token`. Neither packs: the package that `publish.yml` pushes is packed at the
floor, and `Pack` refuses any other Marten.

`CHANGELOG.md` stays the version authority here too. `CreateGitHubRelease` and `Publish` both refuse unless
`GITHUB_REF_NAME` equals `v{version parsed from CHANGELOG.md}`. To release: land the changelog entry first,
then tag that commit.

The GitHub Release carries **no assets** (`ICreateGitHubRelease.AssetFiles => []`). Both packages are consumed
by `PackageReference`; there is nothing a user could usefully download, and attaching a copy of a .nupkg
would only invite installing a file that never went through the trusted-publishing path. The release body
is written by `Build.WriteReleaseNotes` into `artifacts/release-notes.md`: `ICreateGitHubRelease` composes
bodies with `ChangelogTasks.ExtractChangelogSectionNotes`, which only recognises `## ` headings and ends a
section at the first non-bullet line, so pointed straight at our `#`-headed, wrap-bulleted CHANGELOG.md it
returns nothing and the release ships empty. Keep changelog entries as `- ` bullets with wrapped
continuation lines and this keeps working.

`Prerelease` follows the version string (`Version.Contains('-')`), so `0.1.0-rc.1` publishes as a
prerelease and never displaces a latest stable release.

### The NuGet leg

One Ubuntu job runs `dotnet fallout Compile Test Pack Publish` with
`permissions: { contents: read, id-token: write }`, `environment: nuget` and `env: NUGET_USER: lahma`.
One job, not several: more jobs would mean more OIDC exchanges racing the one-key-per-30-s rate limit. No
`paths:` filter: a path filter alongside `tags:` evaluates over the tag commit's diff and can silently skip
the release run.

`Publish` is `.OnlyWhenDynamic(() => ShouldPublish())` and refuses in ordered steps: a non-tag invocation is
a logged *skip* (there is no preview feed), and once past that gate it asserts, in order, that it is on
GitHub Actions, that `NUGET_USER` is set, and that `GITHUB_REF_NAME` matches the changelog version. Only
then does it mint the key, immediately before pushing — the key lives 15–60 minutes and one OIDC token
mints exactly one key. Before it mints the key, it asserts that `artifacts/packages` holds exactly
`PostgresStudio.<version>.nupkg` and `MartenStudio.<version>.nupkg`, and it pushes them with that one key one at a
time, PostgresStudio first, the first failure ending the run, so a PostgresStudio push that fails never lets a
MartenStudio that depends on exactly it reach nuget.org. `--skip-duplicate` keeps a re-run after a partial failure
safe. nuget.org still validates and indexes each package on its own, so for a few minutes after a release MartenStudio
can be listed while its PostgresStudio is not yet restorable. `ReleasePushOrderTests` pins the order and the stop.

The whole ladder is exercisable locally, and should be before any tag:

```powershell
dotnet fallout Pack                                # the package the next steps would push
dotnet fallout Publish --skip                      # skips, and says why
$env:GITHUB_ACTIONS='true'; $env:NUGET_USER='lahma'; $env:GITHUB_REF_NAME='v0.1.0'
dotnet fallout Publish --skip                      # must fail with "GitHub OIDC is unavailable"
```

`Pack` comes first because it is the only step that can fail for a reason the token exchange will never
tell you about: a missing README, a static web asset that did not make it into the nupkg, a package
validation error. Getting a minted key and *then* discovering the package is wrong wastes the one thing
in this path that expires.

That last failure is the success signal: it proves the tagged path routed all the way to the token
exchange. Clear the three variables afterwards.

Three things about the exchange are worth not rediscovering:

- **The POST to `https://www.nuget.org/api/v2/token` must carry a `User-Agent`.** The endpoint sits behind
  Azure Front Door, which answers `400 {"error":"A User-Agent header is required."}` to a request without
  one, *before* looking at the token or the policy — and a bare `HttpClient` sends none. So **a 400 means
  the request never reached the policy**; stop looking at nuget.org settings.
- The OIDC audience is `https://www.nuget.org` (not `nuget`) and the response field is `apiKey` (not
  `api_key`; the build accepts either). The minted key is `add-mask`ed.
- `NUGET_USER` is the nuget.org **profile name of whoever created the trusted publishing policy**
  (`lahma`) — not an email, not an organisation. It is public information and is deliberately a plain
  workflow-level `env:` value, not a secret: a secret would be masked out of exactly the error message that
  names it. Getting it wrong is the most common 401.

### Manual setup, done once, before the first tag

None of these can be done from this repository, and the first tag will fail without the first two:

1. **nuget.org → Trusted Publishing → new policy.** Policy owner `lahma`; Repository Owner `lahma`;
   Repository `marten-studio`; Workflow File `publish.yml` (**filename only** — not `release.yml`, and not
   the `.github/workflows/` path); Environment `nuget`. The policy is not limited to one package id: the key it
   mints pushes both `MartenStudio` and `PostgresStudio`, including an id that does not exist yet (confirmed by the
   policy owner, 2026-10-26).
2. **GitHub → Settings → Environments → `nuget`**, with a deployment branch/tag policy of `v*`. This is the
   second claim the nuget.org policy matches on, and it is what keeps a workflow run from a branch out of
   the publishing path.
3. **The `PostgresStudio` package id** needs nothing more: the policy covers it, so its first version goes out through
   `publish.yml` like every other. Never push a release version by hand - `--skip-duplicate` would then pair packages
   built from different commits; if an id ever had to be claimed by hand, push a `0.0.1-reserve` and unlist it.

Both package ids are names the code carries: a rename would touch the assembly names, the root namespaces,
`_content/PostgresStudio`, the `InternalsVisibleTo` entries and both READMEs.
