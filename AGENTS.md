# AGENTS.md

Guidance for humans and AI agents working in this repository. `CLAUDE.md` imports this file, so keep it
the single source of truth.

**Marten Studio** is an embeddable Blazor Server admin UI for [MartenDB](https://martendb.io), shipped as
one MIT-licensed Razor Class Library. A host adds `AddMartenStudio()` to its container and
`MapMartenStudio()` to its endpoint pipeline, and the studio runs against *that application's own*
configured `IDocumentStore` — browsing document collections and their JSON, inspecting and steering event
streams, projections and the async daemon, running guarded queries and managing schema.

It is **not** a standalone application, not a fleet monitor, and not a connection-string tool. Everything
it knows, it knows because the host configured Marten that way: aliases, duplicated fields, soft delete,
tenancy, projections and metadata columns all come from `StoreOptions`. That is the whole reason a Marten
UI is better than pgAdmin, and it is why the data layer is keyed on `IDocumentStore` and never on a
connection string.

The constraint that governs every design choice here: **registering the studio must never change host
behaviour.** No global styles, no component-library version pinned onto the host, no middleware ordering
requirement, no altered authentication, no second projection daemon. A host that adds the package and
never maps it must be byte-for-byte the application it was.

The full product design — information architecture, every screen, the JSON viewer, the authorization
model, the phased delivery plan — lives in the approved plan at
`C:\Users\marko\.claude\plans\i-d-like-you-to-composed-galaxy.md` until `README.md` and `docs/` exist
(P8). Read it before designing anything; read *this* file before writing anything.

## Hard rules

1. **No new NuGet package without a decision recorded in this file.** The package budget below is
   complete. If a package looks necessary, add a dated row to *Package budget changes* saying what it is,
   what it replaces, and why nothing already present can do the job — before referencing it.
2. **Never hand-edit `.github/workflows/*.yml`.** All three — `build.yml`, `publish.yml`, `release.yml` —
   are generated from the `[GitHubActions]` attributes in `build/Build.CI.GitHubActions.cs`, and any build
   run overwrites them. Change the attribute and re-run the build (`dotnet fallout
   --generate-configuration GitHubActions_publish --host GitHubActions` regenerates just one). A run whose
   generated output differs *aborts* with `Configuration files for GitHubActions (…) have changed` — run
   it again and commit the regenerated YAML. `WorkflowGenerationTests` fails if a file loses its
   `<auto-generated>` header or its load-bearing permission lines.
3. **No MudBlazor, and no third-party UI, CSS or icon library, ever.** Styling is hand-rolled, prefixed
   `ms-`, and driven by the design tokens in `src/MartenStudio/wwwroot/css/marten-studio.css`. An
   embeddable component that injects global styles or pins a component-library version is a component that
   breaks the host's own UI on upgrade; that is the failure Quartz.Dashboard documented and this project
   inherits the rule from.
4. **No raw SQL outside `src/MartenStudio/Internal/Sql/`.** Identifiers are quoted through the builder,
   values are always parameters. Marten only ever hands the studio a runtime `Type`, so the reads *are*
   generated SQL — which means there is exactly one place where an interpolated identifier could become an
   injection, and it is small enough to review.
5. **Every mutating operation is capability-gated in the service layer, and audited.** Hiding a button is
   a UI convenience; the refusal has to live where the operation does, because a Blazor circuit is a
   long-lived object a client can drive. `StudioCapabilityGuard.Require(…)` → scope resolution (with
   `WriteAuthorizationPolicy`) → the operation → `audit.Record`, written on failure as well as on success.
6. **No `async void`.** Component events are `Func<Task>`, handlers are `private async Task` with a
   `try`/`catch` that puts the failure on screen. An `async void` handler's exception escapes the
   synchronization context unobserved and kills the circuit: the page silently stops responding and the
   server log gets an unhandled exception with no component in the stack. `NoAsyncVoidTests` scans `src/`
   and fails on any occurrence. **The lambda form is equally forbidden and the scanner cannot see it:**
   `handler += async (s, e) => …` against an `EventHandler`, or any `async` lambda converted to an
   `Action`, is an `async void` with different spelling and fails in exactly the same way. That is why
   every event this codebase raises is declared `event Func<Task>?` rather than `EventHandler` — an
   `EventHandler` is what *forces* the mistake, so the type is the enforcement and the scanner is only
   the backstop.
7. **A public API change needs a reviewed Verify baseline and a CHANGELOG entry.** The public surface is
   two static classes, two classes and one record; anything else appearing in
   `tests/MartenStudio.Tests/Verify/PublicApiTest_MartenStudio.verified.txt` is a mistake, not a feature.
   Never hand-edit a `.verified.txt`: run the test, read the diff deliberately, say in the pull request
   what moved and why, then accept the baseline.
8. **`.gitignore` must never contain a bare `build` rule.** The Fallout orchestrator lives in `build/`,
   and a stock Visual Studio .gitignore silently untracks the whole thing.
9. **LF line endings everywhere** (`.gitattributes` enforces it), UTF-8 without BOM.
   `TreatWarningsAsErrors` is on and `CS1591` is an **error in `src/`** — the compiler is the lint step.
   `.editorconfig` turns CS1591 off again for `build/`, `tests/`, `samples/` and `*.razor`, where a missing
   doc comment is noise. `BL0005` (setting a `[Parameter]` from outside its component) is an error.
10. **Marten 9 is async-only, and its optional parts are genuinely optional.** There are no synchronous
    LINQ terminals — they throw. Serialize and deserialize through `store.Options.Serializer()`, never
    your own `JsonSerializer`, or a document round-trips through different settings than Marten wrote it
    with. Never touch `StoreOptions.Storage.AllDocumentMappings` (internal). Every metadata column is
    optional — but `Metadata.X.Enabled` alone does not say whether a column exists (verified against
    Marten 9.35's `DocumentTable`, 2026-09-14): `tenant_id` exists iff the type is conjoined, `mt_doc_type`
    iff it is a hierarchy, `mt_deleted`/`mt_deleted_at` iff its `DeleteStyle` is soft (read by casting the
    `IDocumentType` to `Marten.Schema.DocumentMapping`), and only the rest honour `Enabled`; a store with
    `DisableInformationalFields()` has no `mt_last_modified` at all. Build the column set with
    `DocumentTableInfo.FromDocumentType(...).WithPhysicalColumns(...)`, which settles it against
    `information_schema`, and never `select *`.
11. **Never call `store.BuildProjectionDaemonAsync()`.** It starts a *second* daemon alongside the host's
    own, and the two fight over the same advisory locks until one hangs. The only supported way to reach a
    running daemon is the DI-registered coordinator, and its absence is a value —
    `DaemonHosting.NotHostedInThisProcess` — not an error.
12. **The agent definitions in `.claude/agents/*.md` are the only way work is delegated.** A packet is
    routed to exactly one of them; ad-hoc prompting bypasses the rules those files carry (base-commit
    verification, the shared-files list, the reporting format) and produces work that cannot be validated.
13. **A packet routed to Sonnet (`studio-grunt`) must be fully specified** (D21). It may only be given work
    whose expected output the orchestrator can state outright — copy these files with these renames, emit
    this class from this table, run this command and paste the output. If a step needs a decision the
    packet does not make, the correct behaviour is to stop and report the question, never to guess.

## Design decisions (D1–D23)

Every one of these was taken deliberately. Reversing one is allowed; doing it without reading the
rationale is not.

**D1 — `net10.0` only.** Marten 9 targets net9.0 and net10.0, .NET 9 is out of support, and the build
template this repository came from is net10-only. A second target framework would double the test matrix
and the conditional-compilation surface to support a runtime nobody should be deploying.

**D2 — Interactive Server render mode only, and `IsTrimmable=false` said out loud.** Blazor Server is what
lets the studio run against the host's in-process `IDocumentStore`; WebAssembly would need an API surface
that is itself the security problem. `IsTrimmable=false` is stated in the csproj with a comment rather than
left to the default, because Blazor sets component `[Parameter]` properties by name and the document viewer
deserializes into types discovered from `IDocumentType.DocumentType` at run time — a trimmer told it may
cut has no way to see either.

**D3 — Two `PackageReference`s (`Marten`, floor `9.35.0`, and
`Microsoft.AspNetCore.App.Internal.Assets`, floor `10.0.12`, neither with an upper bound) plus
`FrameworkReference Microsoft.AspNetCore.App`.** Everything else the RCL needs — Blazor, SignalR,
authorization, endpoint routing — is in the shared framework, so the package pins no ASP.NET Core patch
onto its host; the assets pack is three `.js` files and an MSBuild target, with no `lib/`, no `ref/` and
no runtime assembly, so it does not either (D22). No `Marten.AspNetCore`: its value is ETag'd HTTP JSON
writers generic over `T`, and the studio only ever has a runtime `Type`. No direct `Npgsql` either; it
arrives through `Weasel.Postgresql`, and adding it would let the two drift.

**D4 — Capabilities are a class of booleans, all defaulting to `false`.** A freshly mapped studio is a
read-only browser; `o.Capabilities = MartenStudioCapabilities.All()` is the one-line, greppable opt-in, and
every disabled control names the exact property a host would have to set. This is Hangfire's
GHSA-7rq6-7gv8-c37h applied to the write axis: the dashboard that is dangerous by default is the one
someone maps without reading the docs.

**D5 — Three authorization layers, plus two process-wide switches.** `AuthorizationPolicy` decides who
gets in; `StoreAuthorizationPolicy` decides which store, database and tenant, resource-based and enforced
on **every** data call rather than only at the selector; `WriteAuthorizationPolicy` decides each mutating
call, against the same resource with the capability name attached. `ReadOnly` and `Capabilities` sit on top
of all three. A startup guard refuses a mapping that answered none of it, because "I forgot to add
`RequireAuthorization`" must not be a silent state.

**D6 — Reads are raw parameterised SQL, writes go through a Marten session.** The studio only knows
document types as runtime `Type`s, so a generic `session.Query<T>()` is not available to it; reads are
built from `IDocumentType` metadata against `IMartenDatabase.CreateConnection(ConnectionUsage.Read)`.
Writes are the opposite: `StoreObjects(IEnumerable<object>)` / `DeleteObjects(IEnumerable<object>)` (both
verified non-generic) keep metadata columns, soft-delete semantics and tenancy exactly as Marten defines
them. The studio never hand-writes document DML; writes go through the session — re-implementing Marten's
write path is how a UI corrupts a store. (There is no `mt_upsert_*` function to call anyway: Marten 9.35
installs none, and the upsert is inline SQL in the generated write path — verified against a live schema
by P7, 2026-09-14.)

**D7 — Document edit shows a round-trip diff before saving.** Marten has no untyped store API, so saving
an edited document means deserializing into the CLR type and serializing it back: any property the type
does not have is *gone*. The dialog lists dropped, changed and added properties before the save happens.
Making the loss visible is the honest answer; silently dropping data is not, and refusing to edit at all
would make the feature useless for the schemas that need it most.

**D8 — Counts are `pg_class.reltuples` estimates by default, prefixed `~`.** An exact `count(*)` on a
10-million-row collection is a sequential scan, and a dashboard that does one per collection per refresh is
a denial of service against the database it is supposed to help you understand. Exact counts are available
on demand, under `statement_timeout`.

**D9 — Document and stream ids travel in the query string.** The hand-rolled router has no catch-all
segment, and Marten ids are frequently strings that contain `/`. Scope (`?store=&db=&tenant=`) lives in the
URL for the same reason a document id does: a link someone pastes into a chat has to reopen the same thing.

**D10 — No SignalR hub in v1.** Pages poll with a `PeriodicTimer` at `RefreshInterval`, paused on hidden
tabs, through a single-flight snapshot cache so that N circuits cost one query per interval rather than N.
Where the daemon is hosted in this process, a lazy observer on `ShardStateTracker` gives sub-second
projection state without any of that. The convention builder already carries an optional hub slot for v2;
adding a hub now would add a host-visible endpoint for a feature that polling covers.

**D11 — Sub-path mounting is ported from Quartz.Dashboard.** Compile-time `/marten` routes are re-rooted at
map time, and `/_blazor`, `blazor.web.js`, `opaque-redirect` and `_content/MartenStudio` are mirrored under
the mount path. This is ~250 lines of genuinely fiddly engineering that already works in production
somewhere; rewriting it would be the single most likely way to ship something that renders locally and
404s behind a path base. There is no "integrate into the host's own Blazor app" mode in v1.

**D12 — The data seam is internal.** Per-area service interfaces (`IDocumentDataService`,
`IEventDataService`, …) with `InternalsVisibleTo` for the two test projects. The *public* surface is two
static classes, two classes and one record, snapshot-tested. Everything a consumer can bind to is
everything we have to keep working.

**D13 — The SQL console is off by default, and its real guard is the transaction.** `RunSql` is a
capability like any other. What makes it safe is `SET TRANSACTION READ ONLY` plus `statement_timeout` and
an optional `SET LOCAL ROLE`, not the statement parser — the parser exists to produce a nicer error
message, and treating it as the security boundary is how these features get CVEs. `README.md` says it
plainly: grant it to people you would give `psql` to.

**D14 — No live SQL tail in v1.** It would require replacing the host's `StoreOptions.Logger`, which is
exactly the "registration changes host behaviour" failure this project refuses, and Marten 9 defaults
`DisableNpgsqlLogging=true` anyway. Every studio-generated grid carries a "Show SQL" disclosure instead,
which answers the question people actually have.

**D15 — Fallout 10.4.0 stable, CHANGELOG.md as the version authority, all three workflows generated,
trusted publishing for nuget.org.** See *Build* and *Release engineering* below. The important half is that
the version lives in one file that a human edits and no tool rewrites, and that the only credential
anywhere in the release path lives for minutes.

**D16 — xunit.v3 3.2.2 and Verify.XunitV3 32.0.0, two test projects both matching `*.Tests`.**
`tests/MartenStudio.Tests` is fast and needs no Docker; `tests/MartenStudio.Integration.Tests` needs
Testcontainers and Playwright. Both match the glob in `ITest.TestProjects`, so one `dotnet fallout Test`
runs everything. The pins are load-bearing — see *Package budget changes*.

**D17 — The demo domain lives in `samples/MartenStudio.SampleDomain` and does not reference
`MartenStudio`.** It is shared by the sample host and by the integration tests, which is the reason it is a
project rather than a folder. The missing reference is deliberate and structural: the studio must work
against a store that knows nothing about it, and a reference here would let that invariant rot without
anyone noticing.

**D18 — The sample host starts a throwaway Postgres when no connection string is configured.** Zero-config
`dotnet run` is what makes the sample a demo rather than a setup exercise. It prints a loud banner saying
what it did, and it throws with guidance when Docker is absent — what it must never do is fall back to
`localhost` silently and appear to work against somebody's real database.

**D19 — Playwright browsers are installed by a Fallout `Browsers` target; locally the browser suite skips
with a reason, on CI a missing browser throws.** A developer should not pay a 150 MB Chromium download for
`dotnet fallout Test`, and CI must never report a green run whose browser tests quietly did not happen. The
skip message names the exact command that would install them.

**D20 — The public API snapshot excludes `ComponentBase`-derived types.** Otherwise every markup edit is a
contract change, the baseline becomes noise, and the one diff that mattered gets approved along with forty
that did not. There is no `PublicApiRendering` annotator in v1.

**D21 — Agent routing.** A packet goes to Sonnet (`studio-grunt`) only when it is mechanical *and* fully
specified: verbatim copies and ports with listed renames, boilerplate emitted from a table in the packet,
scripted runs and artefact collection. Anything involving design choices, security, SQL, authorization,
Marten API verification, Blazor circuit subtleties or test-case design goes to Opus at `xhigh`. Every
Sonnet result is still reviewed by the orchestrator, and by `studio-reviewer` when it touches `src/`.

**D22 — `blazor.web.js` reaches the host through a `PackageReference`, not through a copy in this
package.** As of .NET 10 that file is neither in the shared framework nor embedded in any ASP.NET Core
assembly: it is a static web asset in `Microsoft.AspNetCore.App.Internal.Assets`, which the SDK resolves
only for a project whose `RequiresAspNetWebAssets` is true — and the Web SDK defaults that to true only
for a project that has `.razor` Content items *of its own*. A host that adds Marten Studio and writes no
Blazor components has none, so `GET /_framework/blazor.web.js` answered 404, the studio prerendered,
never became interactive, and nothing in the build said a word. **The package cannot set the property on
the consumer's behalf** — that is a restore-time decision, and NuGet deliberately excludes
package-provided `.props`/`.targets` from restore evaluation (`ExcludeRestorePackageImports`), measured
rather than assumed. A plain `PackageReference` is what does reach the consumer: the pack's
`buildTransitive` targets run in any Web SDK executable that references the studio, directly or
transitively, and define `_framework/blazor.web.js` as **that project's own** static web asset. So the
host serves the script from its own `MapStaticAssets()`, the studio's mapped
`{Path}/_framework/blazor.web.js` endpoint forwards to it, and nothing here ships a frozen copy of a
Microsoft script that would go stale one patch after the package was built. The three-tier resolution in
`MapStudioFrameworkScript` stays — host web root, host endpoint, then a packaged copy that is now
normally absent — because the host's copy must always win where there is one. *The alternative that was
tried and dropped:* vendoring the file, by setting `RequiresAspNetWebAssets` for the RCL itself and
republishing the resolved file as `_content/MartenStudio/_framework/blazor.web.js`. It worked, and it
coupled the shipped script to whatever ASP.NET Core patch built the package.

**D23 — The studio has no forms, so it disables antiforgery on its own endpoints.** Every mutation is a
Blazor event over the circuit; there is no `<form>` and no `<EditForm>` anywhere in `Components/`, and
SignalR's own same-origin check is what stands between a cross-site page and that circuit. The
`<AntiforgeryToken />` in the shell was therefore protecting nothing — and it cost the host a hard
requirement, because `MapRazorComponents` stamps `IAntiforgeryMetadata` that *requires* validation and
the framework refuses to serve such an endpoint when the middleware is absent: a host that never called
`app.UseAntiforgery()` got a 500 for `GET /marten`. "Registering the studio must never change host
behaviour" includes not dictating the host's middleware order, so the token is gone from the shell and
the studio's component endpoints say `.DisableAntiforgery()`. A host that *does* use the middleware is
unaffected — it simply has nothing to validate here. If a screen ever grows a real form, it brings the
token back with it, scoped to that endpoint rather than to the whole studio.
`StudioEndpointsTest.A_host_that_never_calls_UseAntiforgery_still_serves_the_studio` is the regression.

### Package budget changes

**2026-09-14 — initial budget.** Everything in the table above, taken at once as the bootstrap commit.
Three things were verified rather than assumed:

- `dotnet restore marten-studio.slnx` produces **zero NU warnings**. The anticipated `NU1608` from bUnit
  2.11.3 asking for `Microsoft.AspNetCore.*` 10.0.10 under central package management did **not** occur —
  the explicit `10.0.12` rows for `Microsoft.AspNetCore.TestHost` and `Microsoft.AspNetCore.Mvc.Testing`
  are enough on their own, and no `NoWarn` was added. If a future bump reintroduces it, the fix is more
  explicit `PackageVersion` rows in a labelled "framework floor alignment" group — never `NoWarn`.
- The `11.0.0-rc` releases of the `Microsoft.AspNetCore.*` test packages are deliberately not taken.
- `Marten` is a floor rather than an exact pin. The repository's own contract with Marten's API is pinned
  instead, by `tests/MartenStudio.Tests/Marten/MartenApiSurfaceTest.cs` — see *Testing*.

**2026-09-14 — `Microsoft.AspNetCore.App.Internal.Assets` 10.0.12 added to `src/MartenStudio`, and a
vendored copy of `blazor.web.js` removed.** It is the only place that file exists on .NET 10, and nothing
already in the budget can produce it: the shared framework does not carry it and no ASP.NET Core assembly
embeds it (checked — `Microsoft.AspNetCore.Components.Server`/`Web`/`Endpoints` have no manifest
resources). It replaces the build-time vendoring P1.2-fix shipped, which resolved the same pack *for the
RCL* and republished the file as `_content/MartenStudio/_framework/blazor.web.js` — working, but frozen at
whatever ASP.NET Core patch built the package. The reference puts the script in the **consumer's** static
web assets instead, through the pack's `buildTransitive` targets. See D22.

Measured before it was taken, with a nupkg in a local feed and a scratch **API-only** host that has no
`.razor` file, does not set `RequiresAspNetWebAssets`, calls `MapStaticAssets()` and never calls
`UseAntiforgery()` (2026-09-14): `_framework/blazor.web.js` appears in the host's own
`*.staticwebassets.endpoints.json`, `GET /_framework/blazor.web.js` and
`GET /marten/_framework/blazor.web.js` both answer 200 with the real 200 645-byte script,
`GET /marten` is 200, the JS-initializer URL the page advertises is 200 under the studio path, and
`POST /marten/_blazor/negotiate?negotiateVersion=1` answers 200 with a connection token. A second scratch
host with **central package management, transitive pinning and a `.razor` file of its own** also builds
clean — worth checking, because the SDK adds an *implicit* `PackageReference` to this pack for such a
project and a `PackageVersion` row beside an implicit reference is `NU1009`. That is exactly why
`samples/MartenStudio.Sample` no longer sets `RequiresAspNetWebAssets`: with the row in
`Directory.Packages.props`, saying it there was NU1009 — and the sample is a better demonstration
without it, because it is now the shape a real host has.

**2026-09-14 — `GitHubActionsTestLogger` held at 2.4.1, not 3.0.5.** 3.x is a Microsoft.Testing.Platform
logger: it is compiled against `Microsoft.Testing.Platform` 2.0.0, while `xunit.v3` 3.2.2 resolves 1.9.1,
and the two are not assembly-version compatible — **both** test projects failed to compile with `CS1705`
("…uses Microsoft.Testing.Platform … which has a higher version than referenced assembly"). 2.4.1 is the
last VSTest-only release and depends on nothing but `Microsoft.TestPlatform.ObjectModel`, which is exactly
the bridge Fallout 10.4.0's `ITest` drives. Pinning `Microsoft.Testing.Platform` forward instead would
fight xunit.v3's own resolution and was not done. Verified the same day that `dotnet fallout Test` with
`GITHUB_ACTIONS=true` loads the logger and emits its GitHub Actions annotations, and that the TRX still
lands in `artifacts/test-results`. **Exit condition:** revisit when xunit.v3 and Fallout's `ITest` both
speak Microsoft.Testing.Platform v2.

**Held deliberately, and not stale.**

- `xunit.v3` / `xunit.runner.visualstudio` stay at **3.2.2 / 3.1.5** because xunit.v3 4.0.0 drops
  VSTest-mode support, which is not incidental to Fallout 10.4.0's `ITest` — it *is* the interface. `ITest`
  passes `logger trx;LogFileName=`, probes each test project for a `GitHubActionsTestLogger` reference
  before adding `logger GitHubActions`, and parses the resulting TRX against the VSTest `TeamTest/2010`
  schema. Taking 4.x would silently degrade CI reporting to "the run passed or it did not". *Exit:* when
  Fallout's `ITest` speaks Microsoft.Testing.Platform natively.
- `Verify.XunitV3` stays at **32.0.0** because 33.x depends on `xunit.v3.extensibility.core` 4.0.1; 32.0.0
  is the last release that depends on 3.2.2. Moving it forward silently forces xunit.v3 4.x and breaks the
  line above. *Exit:* the same one.
- `Fallout.Common` / `Fallout.Components` stay at **10.4.0** because 11.0.x is the *edge* channel and sorts
  higher only as a versioning artifact — see *Build*. *Exit:* when the stable channel moves past 10.4.
- `NuGet.Frameworks` stays pinned at **7.9.0** in `build/_build.csproj`. Fallout evaluates project files
  in-process (`ITest` asks each test project whether it references `GitHubActionsTestLogger`), which runs
  the installed SDK's own targets inside the Fallout process; those targets bind `NuGet.Frameworks` by
  strong name and SDK 10.0.4xx wants 7.9.0.0, while `Fallout.Components` 10.4.0 resolves 6.14.3
  transitively through `NuGet.Packaging`. App-local assemblies win, so without the pin every `Test` run
  dies in `[MSBuild]::GetTargetFrameworkIdentifier(net10.0)` — a build that compiles and packs fine but
  cannot run a single test. Pinned *forward*, because the runtime binds a higher assembly version than the
  one requested. *Exit:* when Fallout ships a `NuGet.Packaging` new enough to bring 7.9.0 in on its own.

The trusted-publishing exchange uses `Fallout.Common.Utilities.Net` (`CreateRequest`,
`WithBearerAuthentication`, `WithJsonContent`, `GetResponse`, `AssertResponse`, `GetBodyAsJsonObject`),
which arrives with `Fallout.Common` 10.4.0 — no new `PackageReference` anywhere.

## Build

The orchestrator is [Fallout](https://fallout.build) 10.4.0 (stable channel), the maintained hard fork of
NUKE. The CLI is pinned in `.config/dotnet-tools.json` as `fallout.globaltool` (command `fallout`) and
resolves `build/_build.csproj` by folder-name convention.

**10.4.0 is not stale, and 11.0.x is not an upgrade.** Fallout runs two channels: `11.0.x` is *edge* and
`10.4.0` is *stable*, which is newer and a feature superset despite sorting lower. The edge CLI ships under
a different package id (`Fallout.Cli`), which is why `fallout.globaltool` has no 11.x and nothing is
behind. Moving `build/` to 11.0.x would fail to compile — `GitHubActionsAttribute.Env`, which `NUGET_USER`
depends on, does not exist there — and would regenerate the workflows backwards to older action versions.
Do not "update" it.

```powershell
.\build.ps1 Test              # restore, compile, install browsers if asked, run both test projects
.\build.ps1 Test --playwright # ... and install Chromium first (D19)
.\build.ps1 Pack              # the NuGet package into artifacts/packages
.\build.ps1 Browsers          # just the Chromium install
```

`CHANGELOG.md` is the **version authority**: its top section is parsed in `OnBuildInitialized` and passed
to every compile, test and pack as `-p:Version=`. The file is never mutated by the build, and its first
line must parse as a version header (`# 0.1.0`) — **do not add a `# Changelog` title**, it would abort the
build. `Directory.Build.props`'s `VersionPrefix` is only the fallback for a plain `dotnet build`.

The build needs at least one commit: `IHasGitRepository` injects `GitRepository` from the working tree and
fails with `Could not find commit information` on an empty repository.

## Release engineering

A release is cut by pushing a `v*.*.*` tag, which starts **two independent workflows**: `publish.yml`
(nuget.org) and `release.yml` (the GitHub Release). Neither depends on the other, deliberately — a
nuget.org outage must not hold up the release notes, and a release-API hiccup must not hold up the package.

They are separate files because of what each is allowed to hold. A nuget.org trusted publishing policy is
scoped by repository plus workflow **file name** (plus environment), and the nuget.org UI offers no branch
or tag filter — so whichever file the policy names can mint a publishing key on *every* run of that file.
`publish.yml` therefore runs only on a `v*.*.*` tag and holds `id-token: write` with `contents: read`;
`release.yml` holds `contents: write` and `GITHUB_TOKEN` and is not the file the policy names. **The one
workflow that can mint a key must not also hold repository write.** `WorkflowGenerationTests` asserts both
halves, in both directions.

`build.yml` — every push and pull request to `main` — cannot mint anything, because it is not the file in
the policy.

`CHANGELOG.md` stays the version authority here too. `CreateGitHubRelease` and `Publish` both refuse unless
`GITHUB_REF_NAME` equals `v{version parsed from CHANGELOG.md}`. To release: land the changelog entry first,
then tag that commit.

The GitHub Release carries **no assets** (`ICreateGitHubRelease.AssetFiles => []`). MartenStudio is consumed
by `PackageReference`; there is nothing a user could usefully download, and attaching a copy of the .nupkg
would only invite installing a file that never went through the trusted-publishing path. The release body
is written by `Build.WriteReleaseNotes` into `artifacts/release-notes.md`: `ICreateGitHubRelease` composes
bodies with `ChangelogTasks.ExtractChangelogSectionNotes`, which only recognises `## ` headings and ends a
section at the first non-bullet line, so pointed straight at our `#`-headed, wrap-bulleted CHANGELOG.md it
returns nothing and the release ships empty. Keep changelog entries as `- ` bullets with wrapped
continuation lines and this keeps working.

`Prerelease` follows the version string (`Version.Contains('-')`), so `0.1.0-rc.1` publishes as a
prerelease and never displaces a latest stable release.

### The NuGet leg

One Ubuntu job runs `dotnet fallout Compile Test Pack Publish` with
`permissions: { contents: read, id-token: write }`, `environment: nuget` and `env: NUGET_USER: lahma`.
One job, not several: more jobs would mean more OIDC exchanges racing the one-key-per-30-s rate limit. No
`paths:` filter: a path filter alongside `tags:` evaluates over the tag commit's diff and can silently skip
the release run.

`Publish` is `.OnlyWhenDynamic(() => ShouldPublish())` and refuses in ordered steps: a non-tag invocation is
a logged *skip* (there is no preview feed), and once past that gate it asserts, in order, that it is on
GitHub Actions, that `NUGET_USER` is set, and that `GITHUB_REF_NAME` matches the changelog version. Only
then does it mint the key, immediately before pushing — the key lives 15–60 minutes and one OIDC token
mints exactly one key.

The whole ladder is exercisable locally, and should be before any tag:

```powershell
dotnet fallout Pack                                # the package the next steps would push
dotnet fallout Publish --skip                      # skips, and says why
$env:GITHUB_ACTIONS='true'; $env:NUGET_USER='lahma'; $env:GITHUB_REF_NAME='v0.1.0'
dotnet fallout Publish --skip                      # must fail with "GitHub OIDC is unavailable"
```

`Pack` comes first because it is the only step that can fail for a reason the token exchange will never
tell you about: a missing README, a static web asset that did not make it into the nupkg, a package
validation error. Getting a minted key and *then* discovering the package is wrong wastes the one thing
in this path that expires.

That last failure is the success signal: it proves the tagged path routed all the way to the token
exchange. Clear the three variables afterwards.

Three things about the exchange are worth not rediscovering:

- **The POST to `https://www.nuget.org/api/v2/token` must carry a `User-Agent`.** The endpoint sits behind
  Azure Front Door, which answers `400 {"error":"A User-Agent header is required."}` to a request without
  one, *before* looking at the token or the policy — and a bare `HttpClient` sends none. So **a 400 means
  the request never reached the policy**; stop looking at nuget.org settings.
- The OIDC audience is `https://www.nuget.org` (not `nuget`) and the response field is `apiKey` (not
  `api_key`; the build accepts either). The minted key is `add-mask`ed.
- `NUGET_USER` is the nuget.org **profile name of whoever created the trusted publishing policy**
  (`lahma`) — not an email, not an organisation. It is public information and is deliberately a plain
  workflow-level `env:` value, not a secret: a secret would be masked out of exactly the error message that
  names it. Getting it wrong is the most common 401.

### Manual setup, done once, before the first tag

Neither of these can be done from this repository, and the first tag will fail without them:

1. **nuget.org → Trusted Publishing → new policy.** Policy owner `lahma`; Repository Owner `lahma`;
   Repository `marten-studio`; Workflow File `publish.yml` (**filename only** — not `release.yml`, and not
   the `.github/workflows/` path); Environment `nuget`. A policy covers every package the selected owner
   owns; there is no per-package scoping.
2. **GitHub → Settings → Environments → `nuget`**, with a deployment branch/tag policy of `v*`. This is the
   second claim the nuget.org policy matches on, and it is what keeps a workflow run from a branch out of
   the publishing path.

Also worth doing early: **reserve the `MartenStudio` package id**. A rename later would touch the assembly
name, the root namespace, `_content/MartenStudio`, both `InternalsVisibleTo` entries and the README.
