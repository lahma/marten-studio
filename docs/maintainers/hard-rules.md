# Hard rules

This is the full text of hard rules 1 to 16, moved word for word from AGENTS.md on 2026-10-31. AGENTS.md states each rule in brief; this document holds the detail and wins where they differ. In rule 1, 'this file' and 'below' mean AGENTS.md.

## Hard rules 1-16

1. **No new NuGet package without a decision recorded in this file.** The package budget below is
   complete. If a package looks necessary, add a dated entry to *Package budget changes*
   (`docs/maintainers/package-budget-changes.md`) saying what it is,
   what it replaces, and why nothing already present can do the job — before referencing it.
2. **Never hand-edit `.github/workflows/*.yml`.** All four — `build.yml`, `marten-latest.yml`,
   `publish.yml`, `release.yml` — are generated from the `[GitHubActions]` attributes in
   `build/Build.CI.GitHubActions.cs`, and any build
   run overwrites them. Change the attribute and re-run the build (`dotnet fallout
   --generate-configuration GitHubActions_publish --host GitHubActions` regenerates just one). A run whose
   generated output differs *aborts* with `Configuration files for GitHubActions (…) have changed` — run
   it again and commit the regenerated YAML. `WorkflowGenerationTests` fails if a file loses its
   `<auto-generated>` header or its load-bearing permission lines. The `marten-latest` attribute's `Env` is
   `MARTEN_VERSION: latest` and `NPGSQL_VERSION: latest`, so one workflow runs both latest legs (*Build*).
3. **No MudBlazor, and no third-party UI, CSS or icon library, ever.** Styling is hand-rolled, prefixed
   `ms-`, and driven by the design tokens in `src/PostgresStudio/wwwroot/css/studio.css`. There is still exactly
   one stylesheet, and it holds both studios' sections (D26). An
   embeddable component that injects global styles or pins a component-library version is a component that
   breaks the host's own UI on upgrade; that is the failure Quartz.Dashboard documented and this project
   inherits the rule from.
4. **No raw SQL outside the three builders' folders, `src/PostgresStudio.Diagnostics/Internal/Sql/`,
   `src/PostgresStudio/Internal/Sql/` and `src/MartenStudio/Internal/Sql/`.** Identifiers are quoted through the
   builder, values are always parameters. Marten only ever hands the studio a runtime `Type`, and the shared studio
   knows a relation only by its catalog name, so the reads *are* generated SQL — which means there is exactly one
   place per assembly where an interpolated identifier could become an injection, and each is small enough to
   review. The diagnostics engine's builders - the health sweep's and the facts readers' statements, the catalog's,
   `SqlIdentifier`, `SqlLexer` and the read-only guard and session - live in the first; the shared studio's own
   (the SQL console's plans, the browser's rows, Relationships) in the second; the statements only a Marten store
   has (the document, event, daemon and projection reads) in the third, which calls the first's quoting. The
   compiled fence in `HealthQueryConventionTests` exempts each assembly's builders' namespace by name —
   `PostgresStudio.Internal.Sql` in `PostgresStudio.Diagnostics.dll` and in `PostgresStudio.dll`,
   `MartenStudio.Internal.Sql` in `MartenStudio.dll` — and each assembly **only in its own folder** (the first two
   assemblies share a namespace, so the exemption is by assembly and folder, not by namespace alone), so the same test
   refuses a declaration of either namespace, or of one inside it, in any `.cs` or `.razor` file under `src/` outside
   a folder that namespace belongs to, comparing names as C# does (a leading `@` removed, Unicode escapes decoded,
   formatting characters removed).
5. **Every mutating operation, and every read authorized like a write, is capability-gated in the service layer,
   and audited.** (PostgresStudio has only the latter: `RunSql`, `BrowseDatabase`, `ViewDefinitions` and `ViewDatabaseActivity`.)
   Hiding a button is
   a UI convenience; the refusal has to live where the operation does, because a Blazor circuit is a
   long-lived object a client can drive. `StudioCapabilityGuard.Require(…)` → scope resolution (with
   `WriteAuthorizationPolicy`) → the operation → `audit.Record`, written on failure as well as on success.
   A value a visitor could shape reaches the log only through `StudioLogValue`: escaped, a backslash doubled, a name
   bounded at 256 characters and other text at 4,000. That holds in these events: 9200–9205, 9223, 9224, 9235, 9236,
   9245 and 9452 (the per-product dispatchers); 9206, 9207, 9209, 9225, 9226 and 9265 (MartenLog's wrappers); 9260–9263
   (LINQ mode's `Logged*` values); and every Warning that carries a typed route value. `RefusalLogValuesTests` also
   holds every `[LoggerMessage]` template's call sites, at any level, to it. The one exception is 9204's executed
   statement, which is kept whole up to the circuit's 32 KB receive bound, and by its head and tail beyond it.
   A gated column or piece of evidence withheld from a visitor who asked for something else is not a refusal, and is
   not audited (the Health page's evidence, Tenants' volumes, a migration preview's sessions).
6. **No `async void`.** Component events are `Func<Task>`, handlers are `private async Task` with a `try`/`catch` that
   puts the failure on screen. An `async void` handler's exception escapes the synchronization context unobserved and
   kills the circuit: the page silently stops responding and the server log gets an unhandled exception with no
   component in the stack. `NoAsyncVoidTests` scans `src/` and fails on any occurrence. **The lambda form is equally
   forbidden and the source scanner cannot see it:** `handler += async (s, e) => …` against an `EventHandler`, or any
   `async` lambda converted to an `Action`, is an `async void` with different spelling and fails in exactly the same
   way. That is why every event this codebase raises is declared `event Func<Task>?` rather than `EventHandler` — an
   `EventHandler` is what *forces* the mistake, so the type is the enforcement and the scanner is only the backstop. The
   one exception is `StudioState.LinkScopeChanged`, an `event Action?` because its handlers must run before anything is
   awaited: they are synchronous methods that only ask for a render, and `NoAsyncVoidTests` also scans the compiled
   assemblies for a void-returning `[AsyncStateMachine]` method, so an `async` lambda attached to it, or to any
   `Action`, fails the suite.
7. **A public API change needs a reviewed Verify baseline and a CHANGELOG entry.** MartenStudio's surface is
   three static classes, two classes and two records, in
   `tests/MartenStudio.Tests/Verify/PublicApiTest_MartenStudio.verified.txt`, and it must not move because of
   PostgresStudio. PostgresStudio's, in `tests/PostgresStudio.Tests/Verify/PublicApiTest_PostgresStudio.verified.txt`, is
   its five registration types: `PostgresStudioServiceCollectionExtensions`, `PostgresStudioEndpointRouteBuilderExtensions`,
   `PostgresStudioOptions`, `PostgresStudioCapabilities` and `PostgresStudioResource`. Since 0.11 the engine is a package
   of its own with a baseline of its own, `PublicApiTest_PostgresStudioDiagnostics.verified.txt`, which lists type by
   type `PostgresDiagnosticsServiceCollectionExtensions` (`AddPostgresDiagnostics`),
   `PostgresStudioHealthChecksBuilderExtensions`, `PostgresDiagnosticsOptions`, the six inbound types
   (`IPostgresDatabaseSource`, `IPostgresCapacitySource`, `PostgresComputeCapacity`, `PostgresDatabaseRef`,
   `PostgresServerInfo`, `PostgresPlatformKind`: two interfaces and their records), the D31 read model and, since 1.0
   (issue #43), the connection history's four: `PostgresConnectionHistoryServiceCollectionExtensions`
   (`AddPostgresConnectionHistory`), `PostgresConnectionHistoryOptions`, `IPostgresConnectionHistoryStore` - an interface a
   host implements, so a member added later needs a default body (`PublicApiShapeTests`) - and `PostgresConnectionSample`,
   whose `ByApplication` reuses the read model's `PostgresConnectionCounts`.
   Anything else that appears in any baseline is a mistake, not a feature.
   Never hand-edit a `.verified.txt`: run the test, read the diff deliberately, say in the pull request
   what moved and why, then accept the baseline. The read model is extend-only (D31), and `PublicApiShapeTests` holds
   it to that.
   **`docs/health/codes.md` is a contract too, and a row is never deleted.** Every registered check's code has its row,
   with its area, variants, subject kind, studios and the release that first shipped it. A retired check keeps its
   row, marked with the release that retired it, and its code is never reassigned. `HealthCodesTests` holds the table
   to both studios' registries, and its stable columns are a Verify baseline (`HealthCodesTests.verified.txt`), so
   editing or deleting a row is a reviewed baseline change under this rule's process. A new check adds its row in the
   same pull request as its `## <code> <title>` heading.
8. **`.gitignore` must never contain a bare `build` rule.** The Fallout orchestrator lives in `build/`,
   and a stock Visual Studio .gitignore silently untracks the whole thing.
9. **LF line endings everywhere** (`.gitattributes` enforces it), UTF-8 without BOM.
   `TreatWarningsAsErrors` is on and `CS1591` is an **error in `src/`**, both assemblies — the compiler is the lint step.
   `.editorconfig` turns CS1591 off again for `build/`, `tests/`, `samples/` and `*.razor`, where a missing
   doc comment is noise. `BL0005` (setting a `[Parameter]` from outside its component) is an error.
10. **In MartenStudio, Marten 9 is async-only, and its optional parts are genuinely optional.** There are no synchronous
    LINQ terminals — they throw. Serialize and deserialize through `store.Options.Serializer()`, never your own
    `JsonSerializer`, or a document round-trips through settings Marten did not write it with. Never touch
    `StoreOptions.Storage.AllDocumentMappings` (internal). Every metadata column is optional, and `Metadata.X.Enabled`
    alone does not say one exists: `tenant_id` exists iff the type is conjoined, `mt_doc_type` iff it is a hierarchy,
    `mt_deleted`/`mt_deleted_at` iff its `DeleteStyle` is soft (cast the `IDocumentType` to
    `Marten.Schema.DocumentMapping` to read it), only the rest honour `Enabled`, and `DisableInformationalFields()`
    removes `mt_last_modified`. Build the column set with
    `DocumentTableInfo.FromDocumentType(...).WithPhysicalColumns(...)`, which settles it against `information_schema`,
    and never `select *`.
    **And `IDocumentType.DuplicatedFields` is not a list of columns.** Each metadata column a Marten attribute names a
    member for (`[Version]`, `[CreatedAt]`, `[LastModified]`, `[TenantId]`, `[CorrelationId]`, `[CausationId]`,
    `[LastModifiedBy]`) also gets a *search-only* duplicated field, `OnlyForSearching`, named for the *metadata* column
    (`mt_version`) and creating no column. Whatever describes the table's columns enumerates
    `MartenDuplicatedFields.Physical`; only `MetadataAliases` (via `DocumentTableInfo.FindDuplicated`), the search path,
    may see the other half: a column named twice ends the circuit, not the render (issue #1). The fields appear *late*:
    none before a store builds its schema (every unit test here), all once it has served a query (every application).
    Test the shape with `SqlTestStore.WithLinqSearchAliasFor` and prove Marten's half live (history:
    `docs/maintainers/decision-notes.md`, hard rule 10).
11. **In MartenStudio, never call `store.BuildProjectionDaemonAsync()`.** It starts a *second* daemon alongside the host's
    own, and the two fight over the same advisory locks until one hangs. The only supported way to reach a
    running daemon is the DI-registered coordinator, and its absence is a value —
    `DaemonHosting.NotHostedInThisProcess` — not an error.
12. **The agent definitions in `.claude/agents/*.md` are the only way work is delegated.** A packet is
    routed to exactly one of them; ad-hoc prompting bypasses the rules those files carry (base-commit
    verification, the shared-files list, the reporting format) and produces work that cannot be validated.
13. **A packet routed to Sonnet (`studio-grunt`) must be fully specified** (D21). It may only be given work
    whose expected output the orchestrator can state outright — copy these files with these renames, emit
    this class from this table, run this command and paste the output. If a step needs a decision the
    packet does not make, the correct behaviour is to stop and report the question, never to guess.
14. **In MartenStudio, a read or navigation path never calls `AllSchemaNames()`, `AllObjects()`, `ToDatabaseScript()` or
    `CreateMigrationAsync()` — and nothing may describe `CreateOrUpdate` as additive.** (PostgresStudio's read paths
    write nothing, as `FirstNavigationLiveTests` in `PostgresStudio.Integration.Tests` proves for every core page.)
    Below Marten 9.50.3 the first two *apply migrations*, under the database's own `AutoCreate`, when a document type
    has a numeric or HiLo id: **a single `AllSchemaNames()` call on an empty schema creates `mt_hilo` and
    `mt_get_next_hi`**. From 9.50.3 (#5665) the enumeration is offline, and since the 1.1 floor of 9.57 no supported Marten
    has the hazard; the rule stands at every version all the same (a numeric id's runtime `Sequences` still provisions the
    HiLo objects on first use), and `SchemaNoDdlLiveTests` pins that Marten's enumeration creates nothing. The last
    two are slow, connection-hungry and still connect. **Nor does a read path run a Marten LINQ terminal**
    (`ToListAsync`, `CountAsync`, `FirstOrDefaultAsync` and the rest), `ToCommand`, `ExplainAsync`, `ToPreviewCommand`,
    `LoadAsync`, `LoadManyAsync` or a `session.Events` read such as `FetchStreamAsync` or `AggregateStreamAsync`: each
    calls `EnsureStorageExistsAsync`, which creates or migrates its type's storage (below 9.50.3, `mt_hilo` too) when
    the process first asks. Reads use the studio's own SQL; `StorageEnsuringCallTests` allows those calls only in the
    capability-gated writes and F7's LINQ composition (documents, and from 1.1 `QueryRawEvents()`, which is called only with
    no argument, never a tenant: `QueryRawEventsTakesNoTenantTests`), which `MartenLinqCommand` builds into SQL without
    it. From 9.52
    the projection-floor seam (`FetchProjectionFloorAsync` and its two setters) and the high-water advance ensure the
    event storage too: the rebuild dialog reads `mt_event_projection_floors` with the studio's own SQL, and the advance
    is a gated write. Schema names, declared indexes, managed tables, installed functions and what Marten owns (its kind
    map, D27) come from `SchemaDeclarationReader`, which reads `IReadOnlyStoreOptions`, `IDocumentType` and the event
    store's feature schema without a connection; `CheckAsync`, `PreviewAsync` and `DdlAsync` are behind buttons that say
    what they may create on the host's Marten. Everything schema-related is **per database, never per store**: the same
    four members on `IMartenDatabase` (via `Weasel.Core.Migrations.IDatabase`) answer for the resolved database only,
    while `store.Storage`'s apply reaches *every* database a `DynamicMultiple` store knows. Enumerating a dynamic
    tenancy's databases is not read-only either (D27's known limit; `TenancyEnumerationCallTests` fences its call
    sites). Time travel and the stepper fold only through `IAggregateFolder.FoldAsync`, Marten's
    `AggregatorFor<T>().BuildAsync`; no studio code calls `DetermineActionAsync`, `Evolve` or `ISteppableAggregation`
    itself, and `AggregateSteppingTests` holds every step to Marten's single fold at both Marten ends (M1; how each
    shape is stepped: decision-notes.md, hard rule 14).
    **`AutoCreate.CreateOrUpdate` is not additive**: its `Update` delta (Weasel's `TableDelta.WriteUpdate`) drops
    undeclared indexes and extra columns, retypes changed columns, drops a changed primary key `CASCADE` and rebuilds a
    re-partitioned table; only `Invalid` is refused. No screen, comment or doc may say an apply leaves a hand-made index
    alone. Apply and its preview run under `CreateOrUpdate`, never `AutoCreate.All`, so what is read is what is run.
    `MigrationRisk` lists the destructive statements before the typed confirmation, and notes two that remove nothing:
    an index built without `CONCURRENTLY` on an existing table, and Weasel 9.46's partition-index resume, whose
    `DROP INDEX CONCURRENTLY IF EXISTS` of an unattached child, rebuilt and attached at once, is not a drop. The typed
    string travels to the service, never re-supplied by the page. `Check`, `Preview` and `DDL` print the whole database
    (every tenant's partition, every document type's table), so they answer only a visitor the store policy allows for
    the database with `TenantId = null` and, while any document type is hidden, past the database browser's gate; an
    apply is authorized as `(db, null, ApplySchemaChanges)` whatever tenant is selected, as `CreateOrUpdate` reaches
    every tenant. History: decision-notes.md, hard rule 14.
    **The database browser reads the catalog, never Weasel.** Every list and description of a non-Marten object comes
    from `pg_catalog` (never `information_schema`, which hides what the role cannot touch), filtered by
    `nspname = any(@schemas)`, inside `ReadOnlySqlSession`, so `lock_timeout` keeps it off a migration's lock queue and
    `has_*_privilege` answers for `SqlConsoleRole`.
15. **In MartenStudio, open Marten sessions only with `SessionOptions.ForDatabase(resolved.TenantId, resolved.Database)`**
    (or `ForDatabase(resolved.Database)` where the scope has no tenant), never `Store.QuerySession(tenantId)` /
    `LightweightSession(tenantId)`: those ignore the selected database and throw `DefaultTenantUsageDisabledException`
    on a `MultiTenantedDatabases` store, and an unpinned session on a multi-database store reads the store's default,
    not the database the scope named and the audit recorded. **Never run a user-supplied clause through
    `Query<T>(string)` / `QueryAsync(Type, string)`**: Marten's `UserSuppliedQueryHandler` adds no tenant or
    soft-delete predicate, so a typed where clause reads every tenant's rows and every deleted one. A document type
    Marten registers `SingleTenanted()` whatever the store (`DeadLetterEvent` is one) has no `tenant_id` column and no
    Marten predicate: filter on its own `TenantId` property, and prove a sequence is in scope before handing it to an
    API with no tenant predicate. **In both studios, catch interop loss with
    `catch (Exception e) when (StudioLiveUpdates.IsInteropUnavailable(e))`** (a core helper), never a ladder of
    `catch` clauses: `JSDisconnectedException` derives from `Exception`, *not* `JSException`, so
    `catch (JSException) { } catch (InvalidOperationException) { }` misses what every closed tab raises, and an
    exception escaping a component's `DisposeAsync` abandons the rest of that disposal, leaving the
    `DotNetObjectReference` that pins the component undisposed and the page's `CancellationTokenSource` uncancelled. A
    filter still rethrows anything that is a real bug (history: decision-notes.md, hard rule 15).
16. **The core is Marten-free, and the fence is the assembly.** `src/PostgresStudio` and `src/PostgresStudio.Diagnostics`
    reference no Marten, JasperFx or Weasel assembly or package, directly, through a project or transitively:
    `PostgresStudioFenceTests` holds that line at the project files, the restore graphs (`obj/project.assets.json`), the
    built assemblies' references and the test project's output folder, and MartenStudio.Tests' `CoreFenceTests` at the text
    the compiler does not bind (Razor markup, attribute values, crefs and a `MartenStudio` namespace named in a shared
    file, either assembly's). **`PostgresStudio.Diagnostics` has a second fence of its own: no ASP.NET Core.** It has no
    `FrameworkReference`, no `Microsoft.AspNetCore.*` or `Microsoft.JSInterop` package, no Razor SDK or component, and its
    built assembly references none of them, so a worker or console host that uses it loads no web stack; the same test class
    checks the project file, the restore graph (libraries and `frameworkReferences`) and the built references. MartenStudio reaches
    PostgresStudio only through `InternalsVisibleTo`, and is packed with an **exact** dependency on its own
    PostgresStudio build (`[x.y.z]`, D30), which `Pack` asserts in the nuspec and `AddMartenStudio()` checks at
    startup; PostgresStudio reaches `PostgresStudio.Diagnostics` the same way (`InternalsVisibleTo`, an exact
    `PostgresStudio.Diagnostics [x.y.z]`, asserted by `Pack` and checked by `AddPostgresStudio()`, and again by
    `AddMartenStudio()`'s guard). A page route belongs to one assembly of a studio, below that assembly's own compile-time root
    (`/postgres`, `/marten`), and the route table refuses a route two pages claim (`StudioRouteTableTests`).
